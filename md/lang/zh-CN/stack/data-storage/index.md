# 5.1 The Stack :: Data Storage

## 深入讨论

### 一个隐含边界

**Data Storage** 是 Stack 的隐含上边界。它表示内容、状态或资源在显式层开始处理之前保持可用的条件，也表示交互结果之后可以被保留的位置。Model 需要这个边界，因为界面不会从无到有地创造自己的全部对象。在某个东西能够被解释、转换、渲染或作用之前，必须先有某些内容可供读取、取回、接收或引用。

Data Storage 是隐含的，因为 Stack 并不建模存储本身的内部机制。Model 可以依赖一个已存储的资源，但不需要描述这个资源如何被保留的每一个细节。这些关注点属于周围的信息系统。Stack 从某种形式的内容成为活动界面流的一部分时开始。

### 已存储的可用性与活动表示

Data Storage 与 Layer 7: **Digital Data** 之间的区别，就是 **已存储的可用性** 与 **活动表示** 之间的区别。Data Storage 描述某个东西能够持久存在的位置或条件。Digital Data 描述这个东西进入被建模的过程之后，作为计算机可读表示所具有的第一个显式形式。

例如，文档可以存在于文件系统中，记录可以存在于数据库中，响应可以在 API 后面等待。只要它还只是可供访问，它就属于 Data Storage。当界面读取该文档、接收该记录、打开该响应，或以其他方式把资源带入活动流时，它就成为 Layer 7。重要的变化并不是内容突然变得有意义。重要的变化是它现在被表示在 Stack 内部。

### 持久性与转换

Data Storage 关心持久性和可用性。显式 Stack 关心转换。一旦已存储的资源成为 Digital Data，Model 就可以开始描述它会发生什么：它如何被 Structure & Semantics 解释，如何被塑造成 Components, Controls, & Layouts，如何通过 Graphs & Frames 组织，如何由 Renderer 准备，如何通过 Window 交付，并如何由 System 送向 Human Interface。

这种分离很重要，因为存储和转换回答的是不同问题。Data Storage 问的是某个东西是否能够跨时间保持可用。Digital Data 问的是界面当前正在处理哪种活动的二进制、文本、流式或接收到的表示。前者解释保留，后者开始被建模的流。

### 来源与返回边界

在自上而下的流中，Data Storage 作为来源边界。一个已存储的资源被选中或取回，然后作为 Digital Data 进入 Stack。从那一点开始，Model 可以追踪该资源如何被理解、排列、转换并交付给用户。Data Storage 本身不渲染、解析、布局或解释该资源。它只提供活动表示得以开始的条件。

在自下而上的流中，Data Storage 作为返回边界。用户交互可能会请求、创建、更新、删除或以其他方式影响界面流中的某个东西。由此产生的变化可以向上穿过 Stack，直到再次成为 Digital Data。如果该结果必须在即时过程之外保持可用，它就作为被保留的状态返回 Data Storage。Stack 不需要建模每一种写入策略、数据库事务、缓存更新或网络同步步骤，也可以识别该结果已经重新跨入持久性。

### 上下文中的例子

这就是为什么 Data Storage 可以通过许多技术出现，却不由其中任何一种定义。文件系统、MySQL 数据库、MongoDB collection、基于 API 的服务、云对象存储、设备内存区域或流媒体服务，都可以在它们在活动 Stack 之外提供被保留的可用性时充当 Data Storage。一旦某个具体文件、记录、响应、buffer 或 stream 被带入界面流，Model 就把这个活动表示视为 Digital Data。

### 为什么这种分离重要

把 Data Storage 与 Layer 7 分开，可以让 Stack 保持清晰。没有这种区别，Model 就会把某个东西被保存的位置，与界面开始处理它之后它所采取的形式混在一起。这会让 Digital Data 同时负责持久性和活动表示，从而削弱显式层的目的。

通过让 Data Storage 保持隐含，Model 保留了一个清楚的边界：存储围绕界面流，而 Digital Data 开始界面流。这使 Stack 能够描述某个特定活动表示的转换，而不会被它背后所有可能的存储机制缠住。Data Storage 解释被保留的内容可能从哪里来，以及被保留的结果可能回到哪里；Layer 7 开始显式过程，把这些内容转变为界面能够理解、转换并最终呈现的东西。
