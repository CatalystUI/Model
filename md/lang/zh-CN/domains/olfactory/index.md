# 4.5 Domains :: Olfactory

## 深入讨论

在视觉、听觉和触觉之后，**olfactory** domain 描述的是被塑造成可供嗅觉感知的数据。嗅觉数据是为了通过气味被感知而存在的信息，例如释放出的香气、化学信号，或受控的环境气味。visual data 是被看见的，auditory data 是被听见的，tactile data 是被感觉到的，而 olfactory data 是通过鼻子被感知的。

这个 domain 在计算中可能显得不那么熟悉，但原则仍然相同。当系统有意产生某种气味供用户感知时，气味就可以传达信息。训练模拟器可以用烟味表示危险，健康设备可以释放令人平静的香气，沉浸式环境可以用气味强化地点感。在每种情况下，气味都不只是存在；它被作为交互的一部分来使用。

嗅觉数据很特别，因为气味与记忆、环境和身体存在感紧密相连。视觉信号可以被移开视线，声音可以很快停止，触觉提示可以在接触结束时结束。气味却常常会停留。它可以充满一个空间，与周围环境混合，并在原始事件过去后仍然存在。这让嗅觉沟通很有力量，但也更难精确控制。

### 理解嗅觉数据

理解嗅觉数据的一个有用方式，是考虑气味如何被引入、被感知得有多强，以及会停留多久。这些想法可以通过 **来源**、**强度** 和 **持久性** 来描述。一如既往，它们不是模型中的正式类别，但有助于解释气味在实践中如何承载意义。

**来源** 描述气味从哪里来，以及用户如何遇到它。气味可以由可穿戴设备、房间系统或专用外设释放。来源很重要，因为嗅觉输出会受到距离、气流、封闭程度和用户身体位置的影响。不同于通过显示器呈现的像素，或由扬声器定向发出的声波，气味会在周围环境中移动。

**强度** 描述气味有多明显。淡淡的气味可以支持氛围，而更强的气味可能要求注意或传达紧迫性。强度必须谨慎处理，因为气味很容易从有意义变成分散注意力。同一种气味在一个空间里可能显得微妙，在另一个空间里却可能令人难以承受，这取决于环境和用户。

**持久性** 描述气味保持可感知状态的时间。有些气味会很快消散，而另一些会留在空气中、附着在表面上，或在原始事件过去后仍留在记忆里。这使时间控制比许多其他 domains 更复杂。气味可能在系统已经继续前进后仍然继续传达信息，这意味着 olfactory data 必须在设计时考虑持续时间和消散。

### 嗅觉意义

嗅觉输出通过气味表达意义。烟味可以传达危险。干净或花香的气味可以暗示平静、地点或氛围。与食物有关的气味可以支持记忆、食欲或存在感。气味是可感知的形式，而意义来自系统如何在体验中使用这种气味。

这使嗅觉设计特别依赖上下文。同一种气味可能根据记忆、环境、文化和期待而意味着不同的东西。在一个场景中用于安抚的气味，在另一个场景中可能令人不适或分心。不同于标签、图标或语音指令，气味通常不会凭自身传达精确意义。它往往最适合用来强化状态、场景、警告或情绪基调。

嗅觉数据还有一种独特优势：它可以让体验感觉具有身体上的存在感。带有松树香气的森林场景、使用消毒剂气味的医疗训练器，或使用烟味的安全模拟，都可以用视觉和声音未必能完全做到的方式，把信息与身体连接起来。气味可以让界面感觉不像是被观察的东西，而更像是用户已经进入的东西。

### 嗅觉数据与无障碍

olfactory domain 可以在特定情境中支持无障碍，尤其是当气味提供另一种识别事件、环境或状态的方式时。气味可以支持受益于非视觉、非听觉反馈的用户。它也可以帮助训练环境，因为识别气味可能是被建模的真实任务的一部分。

与此同时，嗅觉输出需要特别谨慎，因为气味并不是对每个用户都同样可感知或舒适。有些用户可能嗅觉降低、有过敏、敏感、呼吸方面的顾虑，或对某些气味有强烈负面联想。基于气味的信号也可能在通风不良的空间中被错过，或与已有环境气味混淆。

这正是 domains 帮助澄清设计责任的地方。如果意义通过气味承载，开发者可以询问同一意义是否也应该以 visual、auditory、tactile 或 symbolic 形式提供。目标是保留预期沟通，而不是假设每个用户都能或都应该只通过气味接收它。

### 更广泛体验中的嗅觉数据

嗅觉数据通常作为更广泛体验的一部分最有意义，而不是作为独立界面。模拟可以结合气味、视觉和声音来表示地点。治疗系统可以结合香气、光线和音频来引导平静流程。博物馆装置可以把气味与叙述和图像结合起来，以强化记忆和语境。

在这些情况下，olfactory domain 识别体验中旨在被闻到的部分。它不会取代其他 domains，也不需要独自承载每个细节。它的优势通常是环境性的、氛围性的和联想性的。它可以加深用户对自己所在位置、发生了什么变化，或正在遇到什么情境的理解。

### 嗅觉数据与新兴界面

与视觉、听觉和触觉系统相比，嗅觉界面仍在发展中。大多数用户已经知道如何解释屏幕、扬声器和身体反馈，因为这些模式在日常计算中很常见。基于气味的交互还没有同样共享的语言。因此，即使系统按预期工作，嗅觉输出一开始也可能显得不寻常。

这给 olfactory domain 带来了不同的设计挑战。系统可能需要教用户某种气味意味着什么、什么时候期待它，以及它如何与体验的其余部分相关。视觉图标可以依赖多年熟悉的界面模式。声音效果可以借用常见警报、媒体提示或口语语言。气味在软件中建立起来的惯例更少，因此它的意义可能需要更有意地引入。

技术本身也带来实际限制。气味输出可能需要香氛盒、气流控制、时机管理、消散、清洁或环境校准。这些顾虑并不会让嗅觉交互变得不合法；它们说明为什么这个 domain 需要被清楚命名。一旦气味被识别为一种真实的可感知数据形式，它的限制就可以被直接研究，而不是被当作模型之外的不寻常效果。

简而言之，olfactory domain 描述的是被塑造成基于气味输出的信息。它帮助解释系统如何使用 **来源**、**强度** 和 **持久性** 通过嗅觉进行沟通。当嗅觉数据被妥善处理时，它可以为体验增加存在感、记忆和环境意义，同时仍然立足于每个其他 domain 共有的基本目的：帮助用户感知系统正在传达什么。
