# 4.6 Domains :: Gustatory

## 深入讨论

在嗅觉之后，**gustatory** domain 描述的是被塑造成可供味觉感知的数据。味觉数据是为了通过舌头和口腔被感知而存在的信息，例如甜味、苦味、咸味、酸味、鲜味，或另一种基于味觉的感觉。visual data 是被看见的，auditory data 是被听见的，tactile data 是被感觉到的，olfactory data 是被闻到的，而 gustatory data 是被品尝到的。

这个 domain 可能感觉离日常软件很远，但这种距离本身是有意义的。味觉不是计算机常见的输出方式，所以可借鉴的熟悉例子更少。即便如此，模型仍然应该涵盖它。如果一个系统可以有意通过味觉进行沟通，那么这种交互就应该与视觉、声音、触觉和嗅觉放在同一讨论中。

味觉数据也帮助揭示许多界面假设变得多么狭窄。现代系统通常期待用户通过屏幕接收信息，而把其他感官视为次要或异常。味觉抵抗了这种假设。它提醒我们，人类感知大于当前设备恰好偏好的输出形式。

### 理解味觉数据

理解味觉数据的一个有用方式，是考虑味道如何到达用户、被感知得有多清楚，以及会停留多久。这些想法可以通过 **媒介**、**强度** 和 **持续时间** 来描述。同样，它们不是模型中的正式类别，但有助于解释味觉在实践中如何承载意义。

**媒介** 描述味道如何被传递。味道可以通过食物、液体、可溶材料、电刺激，或专为味觉输出设计的专用设备产生。媒介很重要，因为味觉通常需要与口腔直接接触。系统必须考虑用户如何安全、有意且舒适地接收信号。

**强度** 描述味道有多明显或多可区分。温和的风味可以支持联想或氛围，而更强的味道可以传达更直接的变化。强度必须谨慎处理，因为味觉很容易变得令人不快、分散注意力或带来身体不适。味觉信号需要足够清晰，能被识别，但不能压倒用户。

**持续时间** 描述味道保持可感知状态的时间。有些味道会很快消退，而另一些会在原始交互结束后仍然停留。这使时间控制变得困难，因为信号可能在系统已经继续前进后仍然影响用户。基于味觉的输出应该考虑完整的余味影响，而不只是它被引入的瞬间。

### 味觉意义

味觉输出通过味道表达意义。苦味可以暗示警告。甜味可以暗示奖励、安慰或完成。酸味可以暗示尖锐、惊喜或变化。味道是可感知的形式，而意义来自系统如何在体验中使用这种味道。

这使味觉设计高度依赖上下文。味觉是个人的、文化的、生物的，也是情绪性的。对一个用户来说愉快的风味，对另一个用户来说可能分散注意力或令人不适。味觉还与健康、食欲、记忆和身体舒适感紧密相关，这意味着它应该比许多其他输出形式更谨慎地使用。

当味觉与被表示的体验确实相关时，味觉数据最有力量。营养训练器、医疗模拟、食品教育系统或沉浸式用餐体验，可以通过味觉传达视觉和声音只能间接描述的东西。在这些情境中，味觉不是装饰性效果。它是信息最直接的形式。

### 味觉数据与无障碍

gustatory domain 可以在专门情境中支持无障碍，尤其是当味觉提供另一种识别条件、响应或环境的方式时。当味觉是用户需要理解的内容的一部分时，它可以帮助教育、治疗、训练或模拟。在这些情况下，味觉输出为系统提供了另一条让信息变得可感知的路径。

与此同时，基于味觉的交互承担严肃责任。使用味觉的系统必须考虑过敏、敏感、饮食限制、健康状况、同意、卫生和个人舒适。味觉信号不能被当作颜色变化、声音效果或振动来处理。它会进入身体，因此用户的安全和自主性必须始终位于设计中心。

这正是 domains 帮助澄清设计责任的地方。如果意义通过味觉承载，开发者可以询问同一意义是否也应该以 symbolic、visual、auditory、tactile 或 olfactory 形式提供。目的不是把味觉强行塞进界面，而是在它相关时识别它，并在它并非对每个用户都可用时保留意义。

### 更广泛体验中的味觉数据

味觉数据最常作为更广泛 multisensory experience 的一部分出现。食品模拟可以结合味觉、嗅觉、视觉和声音。医疗训练器可以使用味觉表示现实世界中重要的状态。治疗系统可以把风味与气味或触觉结合起来，引导记忆、注意力或舒适感。

在这些情境中，gustatory domain 识别体验中旨在被品尝的部分。它不需要独自承载整个界面。它的优势通常是具体的、具身的和依赖上下文的。味觉可以传达质量、警告、奖励、真实感或存在感，这些是其他 domains 可以支持但不能完全替代的。

### 味觉数据与模型范围

味觉界面的少见性，正是定义这个 domain 最清楚的理由之一。如果没有像 CatalystUI 这样的模型，我们很容易围绕已经使用的设备来建立对界面的理解：屏幕、扬声器、键盘、控制器和触摸屏。这些工具很重要，但它们不是人机交互的边界。

通过命名 gustatory domain，CatalystUI 让模型保持诚实。它不要求每个系统都使用味觉，也不假装基于味觉的计算很常见。相反，它承认，当系统有意使用味觉进行沟通时，味觉就是一种有效的感知路径。这种承认防止模型变成对当前习惯的描述，而不是对交互本身的描述。

这一点很重要，因为用户不只是信息的观看者。用户通过身体进行感知。有些系统可能只需要屏幕。另一些系统可能需要声音、触觉、嗅觉、味觉，或多个 domains 的组合，才能忠实地沟通。CatalystUI 给开发者一种方式来讨论这些可能性，而不把它们当作模型之外的例外。

简而言之，gustatory domain 描述的是被塑造成基于味觉输出的信息。它帮助解释系统如何使用 **媒介**、**强度** 和 **持续时间** 通过味觉进行沟通。当味觉数据相关并被负责任地处理时，它可以让信息通过身体直接变得可感知，同时提醒我们：界面设计始于用户的感知能力，而不是始于我们习惯构建的设备限制。
