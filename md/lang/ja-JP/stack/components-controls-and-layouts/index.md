# 5.4 The Stack :: Components, Controls, & Layouts

## 詳細な解説

### 最初の可変インターフェイスレイヤー

**Components, Controls, & Layouts** は、解釈された structure が利用可能なインターフェイス素材になるレイヤーです。Layer 6 は表現が何を意味し、どのように整理されているかを説明します。Layer 5 は、その安定した解釈を、配置、更新、相互作用、そして Stack の残りへ向けた準備ができる可変オブジェクトへ変えます。

これは、Model がインターフェイスを単に理解されたものではなく、能動的に利用できるものとして説明し始める最初のレイヤーです。Structure はリソースの意味を説明できますが、ユーザーは structure と直接相互作用するわけではありません。インターフェイスには、値を公開し、意図に応答し、一時的な状態を保ち、より大きな配置に参加できるオブジェクトが必要です。Layer 5 はそれらのオブジェクトを提供します。

### 解釈から使用へ

**Structure & Semantics** と **Components, Controls, & Layouts** の境界は、解釈された形と利用可能な形の境界です。Layer 6 は内容についての安定した理解を生みます。Layer 5 は、その理解を、アクティブな動作中にインターフェイスが扱える形へ適応します。

この区別が重要なのは、解釈された structure とインターフェイスの振る舞いが同じ責任ではないからです。Structure は、値が存在すること、その値がどこに属するか、それを支配する規則を識別できます。Component は、その値を調整可能、表示可能、再生可能、選択可能、編集可能、または別の形で利用可能なものとして公開できます。Structure は内容を説明し、component はインターフェイスにそれを扱う方法を与えます。

したがって Layer 5 は単なる視覚レイヤーではありません。Components、controls、layouts はどの domain にも存在できます。Component はテキスト、音、ハプティックフィードバック、コマンド、文書セクション、メディアリソース、またはインターフェイスの別の利用可能な部分を表すかもしれません。このレイヤーを定義するのは、そのオブジェクトが最終的にどのように知覚されるかではなく、解釈された内容から作られた可変のインターフェイス形式を提供することです。

### Components

**Component** は、解釈された structure から作成される、またはそれに関連づけられる、インターフェイスの論理的で可変な部分です。画像、ラベル、音声トラック、スタイル要素、コマンド、文書セクション、メディアリソース、またはインターフェイスの別の利用可能な部分を表すことがあります。Structure が主に安定した意味に関わるのに対して、component はアクティブな使用に関わります。

Component は、基礎となる内容を扱いやすくするプロパティ、メソッド、状態、振る舞いを公開できます。読み取りまたは変更できる値、実行できる操作、インターフェイスがアクティブな間に追跡できる状態を提供することがあります。これにより Stack の他の部分は、raw な表現や不変の structure を繰り返し扱う代わりに、意味のあるオブジェクトを扱えます。

重要なのは、component が元のリソースの正確な形を保持する必要はないということです。それを単純化したり、一部を組み合わせたり、特定の部分だけを公開したり、その上により便利なインターフェイスを提供したりできます。Layer 5 は実用的であってよいのです。なぜなら、その役割は内容の元の意味を定義することではなく、その意味を利用可能にすることだからです。

### Controls

**Control** は相互作用を扱う component です。Stack の下位レイヤーからルーティングされた相互作用を受け取り、それに応じて何が起こるべきかを決定します。そのため controls は、インターフェイスのユーザー向けの側と内容向けの側が出会う主要な地点の一つです。

Controls は、相互作用を意味のあるインターフェイスの振る舞いへ変える責任を持ちます。Control は値を更新し、操作を発火し、状態を変え、新しい表現を要求し、またはまったく変化を起こさないかもしれません。重要な区別は、control が単にインターフェイスの一部として存在するだけではないということです。ユーザーが system に対して行動する能力に参加します。

Controls は components なので、同じ可変性を共有します。しかし、それらを定義する責任は相互作用の処理です。Component は、ユーザーの意図に直接応答しなくても利用可能なオブジェクトを表せます。Control は、その意図をインターフェイスの流れの中で受け取り、解釈し、作用できる利用可能なオブジェクトを表します。

### Layouts

**Layout** は、controls を含む他の components を、何らかの順序、関係、配置規則に従って並べる component です。視覚インターフェイスでは、これは空間的配置として現れるかもしれません。他の domains では、layout は順序、グループ化、優先度、タイミング、カテゴリ、ルーティング、または別の組織的関係を説明するかもしれません。

Layouts が重要なのは、利用可能なインターフェイスオブジェクトが孤立して存在することはほとんどないからです。Components には文脈が必要です。ユーザーの体験に明確に参加する前に、順序付け、グループ化、整列、重ね合わせ、連続化、または別の形で関係づけられる必要があるかもしれません。Layout は、インターフェイス全体の最上位管理者にならずに、その関係構造を提供します。

これにより layouts は graphs から分かれます。Layout は特定の規則またはパターンに従って components を配置します。Graph は、より大きなインターフェイス文脈全体における発見、整理、関係、ライフサイクルを管理します。Layer 5 は layout オブジェクトそのものを提供し、Layer 4 はそれらのオブジェクトがより大きな操作 frame にどう参加するかを決定します。

### 可変性とアクティブな状態

Layer 5 が可変なのは、インターフェイスがアクティブだからです。解釈された内容がインターフェイスの一部になると、ユーザー意図、システム状態、時間、フォーカス、選択、可視性、再生、入力、その他のライブな条件の変化に応答する必要が生じます。Components、controls、layouts は、それらのアクティブな変化が起こる場所を提供します。

これは Layer 5 が Layer 6 の安定した解釈を置き換えるという意味ではありません。むしろ、その上に構築されます。Component は一時的に変更された値を保持し、control は編集を処理し、layout は配置を再計算するかもしれませんが、それらの変更は下にある解釈された意味とつながったままです。変更が保持されるリソースの一部になる必要がある場合、流れは Structure & Semantics と Digital Data を通って再び上へ移動できます。

可変性により、Layer 5 は保存されないかもしれない一時的なインターフェイス条件も表せます。選択された項目、展開されたセクション、再生位置、hover 状態、focus target、保留中の編集は、永久保存の一部にならなくても、アクティブなインターフェイスにとって重要であることがあります。Layer 5 は、Stack にこれらのライブな条件を説明する明確な場所を与えます。

### 上から下への流れにおける役割

上から下への流れでは、Components, Controls, & Layouts は解釈された structure を受け取り、それを利用可能なインターフェイスオブジェクトへ変えます。Stack は、内容が何を意味するかを知る段階を越え、その内容を相互作用、整理、最終的な提示のために準備し始めています。

この段階で、インターフェイスは、解釈された内容のどの部分を components にするべきか、どの components が相互作用を扱えるべきか、それらの components をどのように配置するべきかを決められます。その結果はまだレンダリングされた frame や system output ではありません。Layer 4 によって整理され、最終的に rendering のために準備されるアクティブなインターフェイスモデルです。

### 下から上への流れにおける役割

下から上への流れでは、Layer 5 はルーティングされた相互作用が意味のある振る舞いになる場所です。下位レイヤーは行動を検出し、変換し、ルーティングできますが、その行動が影響するインターフェイスオブジェクトとの関係で最終的に理解されるのは control です。

Control が相互作用を扱うと、component state を更新し、layout change を要求し、コマンドを発火し、または Structure & Semantics へ戻る必要がある変更を生成するかもしれません。その変更が基礎となる内容に影響する場合、Layer 6 は関連する意味規則に従って変更を検証し整理し、それが再び Digital Data になる前に意味を保つようにできます。このように Layer 5 は、ユーザー意図とインターフェイス状態の間のアクティブな変換点として働きます。

### Graphs & Frames との関係

Layer 5 は利用可能なインターフェイスオブジェクトを生成しますが、それらのオブジェクトが動作する完全な環境として機能するわけではありません。その責任は **Layer 4: Graphs & Frames** に属します。Components、controls、layouts には、それらを整理し、問い合わせ、相互にルーティングし、rendering のために準備し、参加する境界を定義できる、より広い文脈が必要です。

この関係は Model を明確に保ちます。Layer 5 はアクティブなインターフェイスのオブジェクトを定義します。Layer 4 はそれらのより大きな整理を管理し、Stack の下位レイヤーのために準備します。Component は、自分自身の利用可能な状態をどのように表し管理するかを知るべきです。Graph と frame は、その component がより広いインターフェイスの流れにどう収まるかを知るべきです。

### なぜこのレイヤーが重要なのか

Components, Controls, & Layouts は、Stack が解釈から rendering へ直接飛ぶことを防ぎます。システムは、内容を理解してすぐに output を生成するだけでは、明確なインターフェイスを作れません。その解釈された内容が、利用可能で、可変で、配置可能で、相互作用に応答できるものになるレイヤーが必要です。

Layer 5 を Structure & Semantics と Graphs & Frames の両方から分離することで、Model は責任の正確な順序を保ちます。Structure & Semantics は安定した意味を定義します。Components, Controls, & Layouts はその意味をアクティブなインターフェイスオブジェクトへ変えます。Graphs & Frames はそれらのオブジェクトをより大きな操作文脈へ整理します。この分離により、CatalystUI はインターフェイスを visual widgets、raw structures、renderer-specific commands へ還元せずに、domains をまたいで説明できます。
