# 5. The Stack

## 高レベル概要

流れに関わるデータが_どの_種類かを分類した後、次にデータが_どこ_にあるかへ焦点を移せます。ここで、既存の解決策を分析することが非常に役立ちます。特に、それらの違いを調べるときです。各解決策を分解する前に、分析に確かな足場を与える二つの根本的な真実を識別できます。第一に、_データ_はどこかに存在しなければなりません。二進数として、ディスク上に、メモリ内に、または他のどのようなデータ保存形式であってもです。第二に、_人_もまたどこかに存在しなければなりません。画面、ヘッドホン、コントローラー、または他のどのようなインターフェイスの向こう側であってもです。この二つの概念をサンドイッチとして見ます。“Data Storage” が上のパンで、“Human Interface” が下のパンです。この二つは情報の流れの一部として識別されれば明白なので、これらを_暗黙的_と呼びます。流れの性質がそれらの存在を_暗示_するからです。

### Stack のレイヤー

Human Interface から始めると、Stack における最初のレイヤーと大きなパターンを識別できます。それは “system” の存在です。system は、情報が最終的にどのようにユーザーへ届けられるかを整理する役割を持ちます。ほとんどの現代的なコンピューターでは、この役割は “operating system”（“OS”）によって果たされ、コンピューターのハードウェアとソフトウェアの間を橋渡しします。どのような形であれ、情報の流れには、インターフェイス内部の作業をユーザーが体験するものへ接続する最後のステップを完了する system が必要です。

system が有用であるためには、ユーザーがそれと相互作用する方法が必要です。“graphical user interface”（“GUI”）では、これは通常 window によって行われます。しかし CatalystUI Model は、“graphical window” という考え方を狭すぎるものとして扱います。すべてのインターフェイスがグラフィカルとは限らないからです。その代わり、Stack の次のレイヤーである “window” は Layer 2 として定義され、system へのあらゆる「視点」から成ります。これは従来のアプリケーション window、コマンドラインインターフェイス、視覚的なターミナル、音声キャプチャデバイス、またはユーザーが system へ入力を与えたり system から出力を受け取ったりできる任意の文脈かもしれません。

情報が window へ流れ込めるようにするには、インターフェイスが使う内部形式とユーザーが使う知覚可能な形式の間でデータを変換する “renderer” が必要です。これが Layer 3 として働きます。GUI では、これは OpenGL や Vulkan のようなライブラリとして現れ、視覚データを window を通じて表示できる出力に変換します。しかし renderers はグラフィックに限定されません。OpenAL、WASAPI、ASIO、CoreAudio などの音声 renderers は音を生成でき、ハプティック renderers は触覚フィードバックを生成できます。ほとんどの場合、相互作用はほとんど変更されずに通過しますが、赤外線センサーの動作データを処理する場合のように、再解釈または再定義されることもあります。データの domain に関係なく、renderer はインターフェイスで準備されたデータと、出力に使われる domain-specific な形式との間で情報を変換する責任を持ちます。

renderer の後には、インターフェイス内のデータを整理し追跡するレイヤー群があります。これらのレイヤーは最初は区別しにくいかもしれませんが、それぞれが何を提供するかを考えると明確になります。その最初が Layer 4、“Graphs & Frames” です。CatalystUI Model では、“graph” はレンダリングのために準備された整理済み構造を表します。たとえば 3D 世界のオブジェクト、コンポーネントツリー、またはインターフェイスの一部です。“frame” は、利用可能な graphs を含み調整するより大きな文脈を表し、それらを renderer へ渡す準備をします。Web には身近な例があります。“Document Object Model”（“DOM”）は Web ページの要素を graph のように整理し、文書そのものはそれらの要素が存在するより大きな frame を提供します。

この情報形式はユーザーの解釈ではなく renderer に最適化されているため、認識、整理、相互作用のために、データを論理的な形へ分離するレイヤーを導入する必要があります。ほとんどの相互作用処理はここで行われるため、CatalystUI Model は Layer 5 を “Components, Controls, & Layouts” と呼びます。“component” は、画像、ラベル、音声トラック、スタイル要素、または system が提示または整理する他のオブジェクトのような、インターフェイスの論理的な部分です。“control” は、ボタン、トグルスイッチ、スライダー、可変入力などの相互作用を処理します。“layout” は他の components や controls を配置し、意味のある順序へ並べます。グラフィカルインターフェイスでは、これらの違いは視覚要素、クリック可能な controls、行や列として現れるかもしれません。しかし同じパターンはグラフィック以外にも適用されます。音声インターフェイスでは components がトラックや効果音を表し、controls がそれらを再生または調整し、layouts がそれらをグループへ整理できます。このレイヤーは重要です。なぜなら、存在する部分、応答できる部分、それらが graphs に整理され render される前にどう並べられるかという、インターフェイスの利用可能な構造を表すからです。

インターフェイスの論理的な部分を支えるのが “Structure & Semantics”、Layer 6 です。このレイヤーは、データが components、controls、layouts になる前にどのように理解されるべきかを説明します。“Semantics” はデータを読むための規則、つまりそれが何を意味し、どの順序に従い、各部分をどのように理解すべきかを定義します。“Structure” は、それらの規則が適用された後のデータの整理された形です。つまり、このレイヤーは、テキスト、バイト、フィールド、レコードとしてしか存在しないかもしれないデータに、インターフェイスの他の部分が使える意味のある形を与えます。Web では、読み込まれた HTML は Digital Data として始まり、その規則がどのように解釈されるべきかを定義します。解析された文書構造は、元の HTML にそれらの規則を適用した整理済みの結果です。

最後に、Stack の最上部である Layer 7、“Digital Data” そのものに到達します。このレイヤーは、Model の他の部分が読み取り、整理し、提示する前のデータを表します。それはファイル、文書、ストリーム、Web 応答、または同様の表現です。この時点では、まだ structure に形作られておらず、感覚 domain にも割り当てられていません。たとえばテキスト文書は、まだ visual でも auditory でもありません。ただ保存されたテキストです。Stack は後で、それを画面に表示するか、スピーカーで読み上げるかを選び、それによって domain を割り当てることができます。したがって Digital Data は流れの上側の折り返し点です。相互作用は上へ移動して保存内容を変えることができ、保存されたものは後で Stack を下り、ユーザー体験の一部になります。

### Model における Stack の役割

Stack の各部分が識別されたので、Model 全体を説明できます。上から下へ、Stack は “Data Storage”（暗黙）、“Digital Data”、“Structure & Semantics”、“Components, Controls, & Layouts”、“Graphs & Frames”、“Renderers”、“Windows”、“Systems”、そして “Human Interface”（暗黙）で構成されます。七つの明示的なレイヤーは下から上へ番号付けされ、“Systems” が Layer One、“Digital Data” が Layer Seven です。暗黙のレイヤーはこの番号付けの外にあり、流れの終点として機能します。これらを合わせることで、インターフェイスを通る情報の流れを完全に追跡できます。何がプロセスのどこにあるのか、どんな役割を果たしているのか、相互作用の完了にどう貢献しているのかを問うことができます。Stack は正確な実装ではなくパターンを説明するため、システムの内部詳細をすべて知らなくても理解を始められます。これは Model を強力にしている要素の一つです。特に large-language models、machine-learning systems、その他の “AI” 駆動型アーキテクチャによってインターフェイスの内部動作が見えにくくなり得る時代ではなおさらです。

### Stack の実演

#### ドアセンサー

これを示すために、ドアセンサーの例に戻れます。先ほど、この交換を次のように要約しました。ユーザーは進む道を見て、検知エリアに入り、システムがドアを開き、ユーザーが通過してドアが閉じるとサイクルが終わります。Stack を使えば、正確なハードウェア設計を知らなくても、同じ過程をより詳しく説明できます。

行動は “Human Interface” から始まります。ユーザーが出入口へ近づき、“System” に到達します。そこにはコントローラー、配線、電源、モーター機構などが含まれます。“Window” はモーションセンサーや熱検知器によってユーザーの存在を検出し、“Renderer” はその物理信号を利用可能なイベントへ変換します。“Graphs & Frames” は、そのイベントを検知エリアや現在のドア状態を含む、より大きな出入口の文脈に置きます。“Components, Controls, & Layouts” は、ドアを開くべきか、開いたままにするべきか、閉じるべきかという判断そのものを処理します。その判断のために、control は “Structure & Semantics” に依存することがあります。たとえば、感度や遅延時間のような設定がどこにあるかを指定する設定形式です。これらの設定や状態変化は “Digital Data” として表され、保持する必要がある場合は “Data Storage” に置かれます。

判断が行われると、流れは再び Stack を下ります。更新されたドア状態が解釈され、control action へ変換され、出入口の文脈へ戻され、“Renderer” によってハードウェアが実行できるものへ変換され、ドア機構の “Window” を通り、“System” によって実行され、最後に “Human Interface” に受け取られます。最終的に、ユーザーはドアが開くのを見て通過します。

#### Web

二つ目の例として、Web を見てみましょう。Web は、広いユーザーインターフェイスモデルへの既存の試みの中で最も近いものの一つです。特に W3C とその標準化されたインターフェイスがそうです。しかし、主にコンピューター同士の通信を中心に設計されているため、それだけでは Stack のすべての部分を捉えません。典型的な Web ページでは、“Data Storage” はそのページをホストするサーバー、データベース、ファイルシステム、API として表されるかもしれません。ブラウザーが HTML、CSS、JavaScript、画像、類似のリソースを取得すると、それらは “Digital Data” になります。それらを読むための規則、たとえば HTML semantics、CSS styling、JavaScript behavior は “Structure & Semantics” に属します。解釈されると、それらはテキスト、ボタン、フォーム、リンク、画像、layout containers などの利用可能なページ要素となり、“Components, Controls, & Layouts” に属します。その後ページは “Graphs & Frames” に整理されます。これは前述の Document Object Model です。そこから、ブラウザーの “Renderer” がページを表示のために準備します。ブラウザーは operating system が提供する “Window” の中に現れ、それが結果を “Human Interface” へ届ける “System” として機能します。

## Connectors の必要性

CatalystUI の初期開発では、ユーザーインターフェイスを説明するには Stack だけで十分かもしれないと考えていました。最初はそれが妥当に見えました。Stack はすでに、多くの既存モデルよりも明確で完全に、ユーザーインターフェイス内の各部分を識別できます。しかし、それを実際の開発の基盤として使い始めると、まだ何かが足りないように感じました。それぞれの部分が_何_であるかは説明できました。それが_どこ_に属するかも説明できました。しかし、その間にはまだ隙間がありました。データはレイヤー間を_どのように_移動するのか。Stack は経路を与えましたが、あるレイヤーから次のレイヤーへの移動をまだ説明していませんでした。Model を完成させるには、その遷移を定義する必要がありました。ここで “Connectors” は単なる追加概念ではなく、必要なものになります。
