# 4.6 Domains :: Gustatory

## 詳細な解説

嗅覚の後で、**gustatory** domain は味覚のために形づくられたデータを表します。味覚データとは、舌と口を通じて知覚されることを意図した情報です。たとえば甘味、苦味、塩味、酸味、うま味、または味に基づく別の感覚です。visual data が見られ、auditory data が聞かれ、tactile data が感じられ、olfactory data が匂われるのに対して、gustatory data は味わわれます。

この domain は日常的なソフトウェアから遠く感じられるかもしれませんが、その距離には意味があります。味覚はコンピューターにとって一般的な出力方法ではないため、参照できる馴染みある例は少なくなります。それでも、モデルはそれを考慮すべきです。もしシステムが意図的に味覚を通じて伝えられるなら、その相互作用は視覚、音、触覚、嗅覚と同じ議論の中に位置づけられるべきです。

味覚データは、多くのインターフェイス上の前提がどれほど狭くなっているかも明らかにします。現代のシステムはしばしば、ユーザーが画面を通じて情報を受け取ることを期待し、他の感覚を二次的または珍しいものとして扱います。味覚はその前提に抵抗します。それは、人間の知覚が、現在のデバイスがたまたま好んでいる出力形式より大きいことを思い出させます。

### 味覚データを理解する

味覚データを理解するうえで有用な方法は、味がどのようにユーザーへ届き、どれくらい明確に知覚され、どれくらい長く残るかを考えることです。これらの考えは、**媒体**、**強さ**、**持続時間**として説明できます。ここでも、これらはモデルの正式なカテゴリではありませんが、味が実際にどのように意味を運ぶかを説明する助けになります。

**媒体** は、味がどのように届けられるかを表します。味は食べ物、液体、溶ける素材、電気刺激、または味覚に基づく出力のために設計された専用デバイスを通じて届くかもしれません。媒体が重要なのは、味覚が通常、口との直接接触を必要とするからです。システムは、ユーザーがその信号を安全に、意図的に、快適に受け取る方法を考慮しなければなりません。

**強さ** は、味がどれほど目立つか、または区別できるかを表します。穏やかな風味は連想や雰囲気を支え、より強い風味はより直接的な変化を伝えるかもしれません。強さは慎重に扱う必要があります。味はすぐに不快、気を散らすもの、または身体的に不快なものになりうるからです。味覚信号には、ユーザーを圧倒せずに認識されるだけの明確さが必要です。

**持続時間** は、味がどれくらい長く知覚可能なまま残るかを表します。すぐに消える味もあれば、元の相互作用が終わった後も残る味もあります。これはタイミングを難しくします。システムがすでに次へ進んだ後も、信号がユーザーに影響し続けることがあるからです。味に基づく出力は、導入された瞬間だけでなく、後に残る影響全体を考慮して設計されるべきです。

### 味覚的な意味

味覚出力は味を通じて意味を表現します。苦い味は警告を示唆するかもしれません。甘い味は報酬、安心、完了を示唆するかもしれません。酸っぱい味は鋭さ、驚き、変化を示唆するかもしれません。味は知覚可能な形であり、意味はシステムがその味を体験の中でどのように使うかから生まれます。

そのため、味覚デザインは文脈に強く依存します。味は個人的、文化的、生物学的、感情的なものです。あるユーザーにとって心地よい風味が、別のユーザーには気を散らすものや不快なものに感じられることがあります。味覚は健康、食欲、記憶、身体的な快適さとも近い関係を持つため、多くの他の出力形式より慎重に使われるべきです。

味覚データは、味が表されている体験に実際に関係しているときに最も強くなります。栄養トレーナー、医療シミュレーション、食育システム、没入型の食事体験は、視覚と音では間接的にしか説明できないものを味で伝えるかもしれません。そのような状況では、味は装飾的な効果ではありません。それは情報の最も直接的な形式です。

### 味覚データとアクセシビリティ

gustatory domain は、特定の状況でアクセシビリティを支えられます。特に、味が状態、反応、または環境を認識する別の方法を提供する場合です。教育、治療、訓練、シミュレーションにおいて、味がユーザーの理解すべき内容の一部である場合に役立つかもしれません。そのような場合、味覚出力は情報を知覚可能にする別の経路をシステムに与えます。

同時に、味に基づく相互作用には重大な責任があります。味を使うシステムは、アレルギー、過敏性、食事制限、健康状態、同意、衛生、個人的な快適さを考慮しなければなりません。味覚信号は、色の変化、効果音、振動のように扱うことはできません。それは身体の中に入るため、ユーザーの安全と主体性は設計の中心にあり続けなければなりません。

ここで domains は、設計上の責任を明確にする助けになります。意味が味によって運ばれる場合、開発者は同じ意味が symbolic、visual、auditory、tactile、または olfactory にも利用可能であるべきかを問うことができます。目的は味をインターフェイスに押し込むことではなく、関連があるときにそれを認識し、すべてのユーザーに利用可能でないときに意味を保つことです。

### より広い体験における味覚データ

味覚データは、多くの場合、より広いマルチセンサリーな体験の一部として現れます。食のシミュレーションは、味を嗅覚、視覚、音と組み合わせるかもしれません。医療トレーナーは、現実世界で重要になる状態を表すために味を使うかもしれません。治療システムは、記憶、注意、快適さを導くために、風味を香りや触覚と組み合わせるかもしれません。

このような状況では、gustatory domain は体験のうち味わわれることを意図した部分を識別します。それだけでインターフェイス全体を運ぶ必要はありません。その強みは通常、具体的で、身体化され、文脈に依存しています。味は、他の domains が支えられても完全には置き換えられない方法で、品質、警告、報酬、現実感、存在感を伝えることがあります。

### 味覚データとモデルの範囲

味覚インターフェイスが珍しいことは、この domain を定義する最も明確な理由の一つです。CatalystUI のようなモデルがなければ、私たちはすでに使っているデバイス、つまり画面、スピーカー、キーボード、コントローラー、タッチスクリーンを中心にインターフェイス理解を組み立てがちです。これらの道具は重要ですが、人間とコンピューターの相互作用の境界ではありません。

gustatory domain に名前を与えることで、CatalystUI はモデルを誠実なものに保ちます。すべてのシステムに味を使うことを要求するわけではなく、味に基づくコンピューティングが一般的だと装うわけでもありません。むしろ、システムが意図的に味を使って伝えるとき、味は知覚への有効な経路であると認識します。その認識により、モデルが相互作用そのものの説明ではなく、現在の習慣の説明になってしまうことを防ぎます。

これは重要です。ユーザーは情報の視聴者だけではないからです。ユーザーは身体を通じて知覚します。画面だけで足りるシステムもあるかもしれません。他のシステムでは、忠実に伝えるために音、触覚、嗅覚、味覚、または複数の domains の組み合わせが必要かもしれません。CatalystUI は、開発者がそれらの可能性をモデルの外にある例外として扱わずに議論する方法を与えます。

要するに、gustatory domain は味に基づく出力へ形づくられた情報を表します。それは、システムが **媒体**、**強さ**、**持続時間** を使って味覚を通じてどのように伝えるかを説明する助けになります。味覚データが関連し、責任をもって扱われるとき、それは情報を身体を通じて直接知覚可能にしながら、インターフェイス設計が私たちの慣れたデバイスの制約ではなく、ユーザーの知覚能力から始まることを思い出させます。
