# 4.3 Domains :: Auditory

## 詳細な解説

visual domain の後で、**auditory** domain は聴覚のために形づくられたデータを表します。聴覚データとは、音を通じて知覚されることを意図した情報です。たとえば話し言葉、音楽、アラート、トーン、またはユーザーが聞くことで理解するその他の出力です。visual data が意味を視覚で読める形へ配置するのに対して、auditory data は意味を時間に基づく音へ配置します。

これにより、auditory domain は visual domain と重要な点で異なります。視覚情報はしばしば一度に見渡せますが、聴覚情報は通常、時間の中で展開します。ユーザーは画面を一目見て複数の関係をすぐに認識できるかもしれませんが、音は順番に聞かれなければなりません。そのため、auditory data はタイミング、順序、長さ、リズムに強く依存します。意味は、何が聞こえるかだけではなく、いつ聞こえるか、そしてどのように変化するかにもあります。

保存された音声ファイルは、音声データを含んでいるだけでは auditory ではありません。保存され、エンコードされ、または抽象的に表現されている間、それはまだ symbolic です。システムがそれを知覚可能な音として生成したとき、それは auditory になります。スクリーンリーダーによって読み上げられる書かれたテキスト、チャイムへ変換される通知、音楽で表現されるゲームイベントも同じです。いずれの場合も、システムは情報を取り、それを聴覚に結びつけています。

### 聴覚データを理解する

聴覚データを理解するうえで有用な方法は、**内容**、**タイミング**、**トーン**を考えることです。これらはモデルの正式なカテゴリではありませんが、音が視覚とは異なる形で意味を運ぶ仕組みを説明する助けになります。

**内容** は、音が何を伝えるかを表します。音声出力では、読み上げられている言葉かもしれません。音楽では、旋律、和声、進行かもしれません。通知では、何かが起きたことをユーザーに知らせる認識可能なパターンかもしれません。聴覚内容とは、ユーザーが聞いて理解することを期待されるものの実質です。

**タイミング** は、音がいつ起こり、どれくらい続くかを表します。警告音が遅すぎると、有用性を失うかもしれません。話し言葉のメッセージが速すぎると、追いにくくなるかもしれません。ユーザーの行動に即座に反応する音楽はつながっているように感じられますが、遅れた音はシステムを切り離されたもののように感じさせることがあります。聴覚データは動きの中で経験されるため、タイミングは重要です。

**トーン** は、音の質や性格を表します。柔らかなチャイム、鋭いビープ音、落ち着いた話し声は、すべて短い聴覚信号であっても非常に異なる意味を伝えられます。トーンは、緊急性、雰囲気、確認、警告、完了をユーザーが理解する助けになります。それは音に感情的かつ実用的な性格を与えます。

### 聴覚的な意味

聴覚出力は音を通じて意味を表現しますが、音そのものを意味全体と取り違えるべきではありません。警告のビープ音は問題を伝えるかもしれませんが、ビープ音そのものが問題ではありません。読み上げられたラベルはテキストを伝えるかもしれませんが、声は基礎構造ではありません。音楽的な合図は成功、危険、移行を伝えるかもしれませんが、意味はシステムがその合図を体験の中でどのように使うかから生まれます。

この区別は重要です。音は強力でありながら、必ずしも精密ではないからです。短いトーンはユーザーの注意を引くかもしれませんが、何が起きたかは説明しないかもしれません。話し言葉のメッセージは明確に説明できるかもしれませんが、視覚的な手がかりより時間がかかることがあります。音楽は体験の感じ方を形づくるかもしれませんが、正確な指示は伝えないかもしれません。聴覚デザインは、音がシステムの表すべき意味の種類と一致しているときに最も強くなります。

聴覚データは、視覚データとは異なる形でユーザーに影響します。音は、ユーザーがシステムを直接見ることを要求せずに届くことができるからです。タイマーは別の部屋から鳴ることができます。ナビゲーションアプリは、ユーザーの目が道路に向いたまま話すことができます。スクリーンリーダーは、ユーザーが視覚に依存せずにソフトウェアを操作できるようにします。これにより auditory domain は、注意が分散しているとき、視覚が使えないとき、または音が最も明確なコミュニケーション経路であるときに特に価値を持ちます。

### 聴覚データとアクセシビリティ

auditory domain はアクセシビリティの中心です。視覚の中に閉じ込められかねない情報を運ぶことができるからです。テキストは話されることができます。インターフェイスの状態は読み上げられることができます。ナビゲーションは音で導かれることができます。一部のユーザーにとって、聴覚出力は強化ではありません。それはシステムが利用可能になるための主要な方法です。

同時に、聴覚情報が意味を伝える唯一の方法である場合、アクセシビリティ上の懸念も生じます。音だけとして存在する警告は、ろう者または難聴のユーザーに見逃されるかもしれません。話し言葉の指示は、騒がしい環境では追いにくいかもしれません。効果音は行動を確認できるかもしれませんが、その確認の別の表現がなければ、意味は聴覚だけに依存することになります。

ここで domains は、システムが実際に何をしているかを明らかにする助けになります。重要な意味が音だけで運ばれている場合、開発者はそれが symbolic、visual、tactile、または別の形式でも利用可能であるべきかを問うことができます。目的は聴覚デザインを弱めることではなく、ユーザーが実際にシステムを知覚するさまざまな方法をまたいで意味を保つことです。

### より広い体験における聴覚データ

聴覚データはしばしば他の domains と並んで働きます。動画プレイヤーでは、映像が動きを運ぶ一方で、音が話し声や音楽を運ぶかもしれません。ゲームでは、音声が距離、危険、雰囲気、フィードバックを伝えるかもしれません。オペレーティングシステムでは、音が通知、エラー、確認を支えるかもしれません。いずれの場合も、auditory domain は聴覚のために形づくられた体験の部分を識別します。

音が他の知覚形式と統合されると、より大きなマルチセンサリーな交換の一部になることがあります。視覚アニメーションと組み合わされた音は、行動が完了したように感じさせることがあります。地図と組み合わされた音声案内は、どちらか単独よりも明確にユーザーを導くことがあります。警告音と組み合わされた振動は、通知を見逃しにくくすることがあります。聴覚部分にはなお独自の役割がありますが、完全な体験は domains がどのように連携するかに依存することがあります。

要するに、auditory domain は聞こえる出力へ形づくられた情報を表します。それは、システムが音を使って内容、タイミング、トーン、フィードバックをどのように伝えるかを説明する助けになります。聴覚データがうまく扱われているとき、ユーザーはシステムが提示しているものを聞き、何が変わったかを認識し、体験のすべての部分が見える必要なしに応答できます。
