# 4.2 Domains :: Visual

## 詳細な解説

**symbolic** domain が、データが特定の感覚にまだ結びつけられていない段階を表すのに対して、**visual** domain は、データが視覚のために形づくられた段階を表します。視覚データとは、見られることを意図した情報です。たとえば画像、レンダリングされたテキスト、または目に見えるコントロールです。重要な区別は、そのデータがいつか画面に現れる「かもしれない」かどうかではなく、現在の相互作用における役割が視覚を通じて伝えることなのかどうかです。

つまり、視覚データを、その背後にある保存形式と混同してはいけません。画像データを含むファイルは、保存された情報としてだけ存在している間はまだ symbolic です。テキストの段落も、文字、マークアップ、または別の抽象的表現としてだけ存在している間はまだ symbolic です。システムがそれを、ユーザーが見て解釈できる形で提示したとき、それは visual になります。変化しているのは、データがより重要になることではありません。変化しているのは、その伝達方法が表現から知覚へ移ったということです。

視覚データは特に一般的です。視覚は多くの関係を同時に伝えられるからです。大きさ、色、間隔、方向、グループ化、動きはすべて、それが何であり、どこに属し、それに対して行動できるかどうかをユーザーが理解する助けになります。だからこそ、視覚インターフェイスはしばしば即時的に感じられます。ユーザーはウィンドウ、ウェブページ、ゲームシーンを一目見るだけで、すべての言葉を読む前に意味を得ることができます。システムは単にデータを表示しているのではなく、データを目に見える体験へと配置しているのです。

### 視覚データを理解する

視覚データを理解するうえで有用な方法は、**配置**、**外観**、**状態**を考えることです。これらは CatalystUI Model における正式なサブドメインでも必須カテゴリでもありませんが、視覚情報がどのように意味を伝えるかを認識するための実践的な手がかりになります。

**配置** は、視覚データがどこに現れ、周囲の情報とどのように関係するかを表します。段落の上に置かれた見出しは所属関係を伝えます。フォームの近くに置かれたボタンは関連性を伝えます。他の内容の上に置かれたメニューは一時的な優先度を伝えます。配置が重要なのは、ユーザーが見える物体を孤立して知覚するのではなく、見える物体どうしの関係を知覚するからです。

**外観** は、視覚データがユーザーにどのように現れるかを表します。形、色、タイポグラフィ、コントラスト、画像表現はすべて、ユーザーが何を見ていると考えるかに影響します。テキストの一部は、スタイルによってタイトル、警告、リンクのように見えることがあります。長方形は、境界線、間隔、周囲の文脈によって、ボタン、パネル、装飾のように見えることがあります。外観は視覚データに認識可能な形を与えます。

**状態** は、視覚的に伝えられている現在の条件を表します。コントロールは、アクティブ、無効、選択済み、フォーカス中、読み込み中、非表示のように見えることがあります。これらの状態は重要です。ユーザーの次の行動は、インターフェイスが何をする準備ができているように見えるかに依存することが多いからです。視覚状態がシステムの実際の状態と一致していない場合、基礎となるロジックが技術的に正しくても、インターフェイスは混乱を招きます。

### 視覚的な意味

視覚出力は意味を表現しますが、意味そのものと取り違えるべきではありません。赤い枠線は何かが間違っていることを伝えるかもしれませんが、枠線そのものがエラーではありません。アイコンは行動を表すかもしれませんが、アイコンそのものが行動ではありません。レイアウトは階層を示すかもしれませんが、レイアウトそのものが基礎構造ではありません。視覚データは意味の感覚的な表現であり、意味の完全な源ではありません。

この区別は、よくある設計上の誤りを防ぐ助けになります。つまり、何かがどう見えるかに過剰な責任を負わせ、その意味を保たないことです。インターフェイスがエラーを伝えるために色だけに依存している場合、意味は一つの視覚信号の中に閉じ込められます。アイコンに補助的なラベル、説明、またはアクセシブルな意味がない場合、システムはきれいに見えても理解しにくくなることがあります。視覚的な明確さは、見える形がその背後にある意図を忠実に表しているときに最も強くなります。

視覚データには独特のリスクもあります。ユーザーは自分が見たものを信頼しがちだからです。何かがクリックできるように見えれば、ユーザーはそれが反応すると期待します。何かが無効に見えれば、ユーザーはそれが反応しないと期待します。何かが選択済みに見えれば、ユーザーはシステムがそれを選択済みとして扱うと期待します。見える提示と実際の動作が食い違うと、プログラムが書かれたとおりに動作していても、ユーザーはインターフェイスが壊れているように感じます。

### 視覚データとアクセシビリティ

visual domain は、情報が視覚だけを通じて伝えられている場面を識別するため、アクセシビリティについて考えやすくします。エラーが色だけで示される場合、グラフが画像だけで示される場合、進行状況がアニメーションだけで示される場合、その意味はすべてのユーザーに利用可能とは限りません。問題は視覚的な伝達が悪いことではありません。問題は、視覚的な伝達を別の形へ翻訳する必要があるかもしれないことです。

ここで domains は診断ツールとして有用になります。意味が現在どこにあるのかを問う助けになるからです。それは visual だけでしょうか。symbolic にも表せるでしょうか。音、触覚、または別の出力形態でも利用可能にすべきでしょうか。これらの問いに答えることで、開発者はアクセシビリティを後回しにするのではなく、異なる知覚の種類をまたいで同じ意味を保つことができます。

### より広い体験における視覚データ

視覚データは、純粋に視覚的ではない体験にも参加できます。動画プレイヤーは動く画像と音を組み合わせるかもしれません。ゲームはグラフィック、音楽、コントローラーのフィードバックを組み合わせるかもしれません。オペレーティングシステムは、ウィンドウ、アラート、入力デバイスを一つの大きなやり取りに組み合わせるかもしれません。このような状況では、visual domain は視覚に向けられた体験の部分を識別し、他の domains は関与している追加の知覚形態を説明します。

これにより、モデルは精密なままでいられます。視覚インターフェイスは自動的にユーザーインターフェイス全体を意味するわけではなく、マルチセンサリーな体験も、その中にある視覚部分を消し去るわけではありません。各 domain は、意味がどのように運ばれているかを識別する助けになります。visual domain は一つの具体的な問いに答えます。どの情報が、ユーザーに見えるように形づくられているのか。

要するに、visual domain は symbolic representation から視覚で読める出力への移動を表します。それは、すべてのインターフェイスをグラフィックに還元せずに、見える情報について議論する方法を与えてくれます。視覚データがうまく扱われているとき、ユーザーはシステムが提示しているものを認識し、何に対して行動できるかを理解し、自信を持って応答できます。
