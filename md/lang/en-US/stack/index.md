# 5. The Stack

## Per-Topic Summary

After classifying _what_ type of data is involved in the flow, we can then focus on _where_ the data is located. This is when analyzing existing solutions can really come in handy, especially when examining their differences. Prior to dissecting each solution, we can identify two fundamental truths to give our analysis a solid footing: first, the _data_ must exist somewhere, whether being stored as binary, on a disk, in memory, or any other form of data storage, and second, a _person_ must also exist somewhere, whether on the other end of a screen, headphones, controller, or any other form of interface. We will view these two concepts as a sandwich, with “Data Storage” as the top bun and a “Human Interface” as the bottom bun. Since these two concepts are obvious, once identified, as parts of the flow of information, we’ll call them _implied_, since the nature of the flow _implies_ their existence.

### The Layers of The Stack

Starting from the human interface, we can begin identifying the first layer and major pattern in the Stack: the presence of a “system.” A system is responsible for organizing how information is ultimately delivered to the user. In most modern computers, this role is fulfilled by an “operating system” (“OS”), which bridges the gap between a computer’s hardware and its software. Regardless of its form, in any flow of information, a system must exist to complete the final step that connects the interface’s internal work to what the user experiences.

For a system to be useful, the user needs some way to interact with it. In a “graphical user interface” (“GUI”), this is typically done through a window. However, the CatalystUI Model treats the idea of a “graphical window” as too narrow, since not every interface is graphical. Instead, the next layer in the Stack, a “window,” is defined as Layer 2, and consists of any “view” into a system. This may be a traditional application window, a command-line interface, a visual terminal, an audio-capture device, or any other context in which the user can provide input to or receive output from the system.

To allow information to flow into a window, a “renderer” is needed to transform data between the internal form used by the interface and the perceivable form used by the user, acting as Layer 3. In a GUI, this often appears as a library such as OpenGL or Vulkan, converting visual data into output that can be displayed through a window. However, renderers are not limited to graphics. Audio renderers, such as OpenAL, WASAPI, ASIO, or CoreAudio, can produce sound, while haptic renderers can produce tactile feedback. In most cases, interactions pass through with little modification but may become reinterpreted or redefined, such as processing motion data from an infrared sensor. Regardless of the data’s domain, the renderer is responsible for converting information between the interface’s prepared data and the domain-specific form used for output.

Following the renderer is a set of layers that organize and track data within the interface. These layers can be difficult to distinguish at first, but it becomes clearer once we consider what each layer provides, the first of which is Layer 4: “Graphs & Frames.” In the CatalystUI Model, a “graph” represents organized relationships among interface objects, such as an object in a 3D world, a component tree, or a subsection of an interface. A “frame” represents the larger current context that contains and coordinates the available graphs, preparing them for the renderer. A familiar example can be found on the web: the “Document Object Model” (“DOM”) organizes the elements of a webpage like a graph, while the document itself provides the larger frame in which those elements exist.

Since this form of information is organized for renderer-facing preparation rather than direct user interpretation, we need to introduce a layer that separates data into its logical form to be recognized, organized, or interacted with. This is where most interaction processing occurs, so the CatalystUI Model refers to Layer 5: “Components, Controls, & Layouts.” A “component” is any logical, usable part of the interface, such as an image, label, audio track, style element, or other object the system may present or organize. A “control” processes interactions, such as a button, toggle switch, slider, or variable input. A “layout” arranges other components or controls and places them in a meaningful order. In a graphical interface, these distinctions may appear as visual elements, clickable controls, and rows or columns. However, the same pattern applies outside of graphics as well: an audio interface may use components to represent tracks or sound effects, controls to play or adjust them, and layouts to organize them into groups. This layer is essential because it represents the usable structure of the interface: the parts that exist, the parts that can respond, and the way those parts are arranged before being organized into graphs and prepared for rendering.

Backing the logical parts of the interface is “Structure & Semantics,” Layer 6. This layer describes how data should be understood before it becomes components, controls, or layouts. “Semantics” define the rules for reading the data: what it means, the order it follows, and how each part should be understood. “Structure” is the organized form of that data after those rules have been applied. In other words, this layer takes data that may exist only as text, bytes, fields, or records and gives it a meaningful shape that the rest of the interface can use. On the web, for example, loaded HTML begins as digital data, and its rules define how it should be interpreted. The parsed document structure is the organized result of applying those rules to the original HTML.

Finally, we reach the top of the Stack, Layer 7: “Digital Data” itself. This layer represents data after it has entered the active interface flow in a computer-readable form, but before the rest of the Model has interpreted, organized, or presented it. It may be a file, document, stream, web response, or another similar representation. At this point, it has not yet been shaped into a structure or assigned to a sensory domain. A text document, for example, is not yet visual or auditory. It is an active text representation that the Stack can interpret later. The Stack may choose to display it on a screen or read it aloud through a speaker, thereby assigning it to a domain. Digital Data is therefore the upper turning point of the flow: an interaction can move upward and change what may be stored, and stored content can later move back down the Stack to become part of the user’s experience.

### The Role of the Stack in the Model

With each piece of the Stack now identified, we can describe the Model as a whole. From top to bottom, the Stack consists of “Data Storage” (implied), “Digital Data,” “Structure & Semantics,” “Components, Controls, & Layouts,” “Graphs & Frames,” “Renderers,” “Windows,” “Systems,” and the “Human Interface” (implied). The seven explicit layers are numbered from the bottom up, with “Systems” as Layer One and “Digital Data” as Layer Seven. The implied layers sit outside this numbering and serve as the endpoints of the flow. Together, they give us a complete way to trace the flow of information through an interface. They allow us to ask where something is in the process, what role it is serving, and how it contributes to the interaction being completed. Because the Stack describes the pattern rather than an exact implementation, we do not need to know every internal detail of a system to begin understanding it. This is part of what makes the Model powerful, especially in an age where large-language models, machine-learning systems, and other forms of “AI”-driven architecture can make the inner workings of an interface harder to see.

### Demonstrating the Stack

#### A Door Sensor

To demonstrate this, we can return to the door sensor example. Earlier, we summarized the exchange as follows: the user sees a path forward, enters the detection area, the system opens the door, and the cycle ends once the user passes through and the door closes. The Stack lets us describe that same process in more detail without knowing the exact hardware design.

The action begins at the “Human Interface,” where the user approaches the doorway, and reaches the “System,” such as a controller, wiring, power source, and motor assembly. The system receives the physical signal through the doorway hardware. The “Window” associates that signal with the doorway’s detection context, while the “Renderer” converts or maps it into a usable event. “Graphs & Frames” places the event within the larger doorway context, including the detection area and current door state. “Components, Controls, & Layouts” handles the decision itself, determining whether the door should open, remain open, or close. To make that decision, the control may rely on “Structure & Semantics,” such as a configuration format that specifies where settings like sensitivity or delay timing are located. Those settings and state changes are then represented as “Digital Data,” and, if they need to be retained, placed into “Data Storage.”

Once the decision is made, the flow moves back down the Stack: the updated door state is interpreted, turned into a control action, placed back into the doorway context, converted by the “Renderer” into something the hardware can perform, passed through the “Window” of the doorway mechanism, carried out by the “System,” and finally received by the “Human Interface.” Finally, the user sees the door open and walks through.

#### The Web

For a second example, we can look at the web. The web is one of the closest existing attempts at a broad user-interface model, especially through the W3C and its standardized interfaces. However, because it is mainly designed around communication between computers, it does not capture every part of the Stack on its own. On a typical webpage, “Data Storage” may be represented by the server, database, file system, or API-backed service that hosts the page. When the browser fetches HTML, CSS, JavaScript, images, and similar resources, those become “Digital Data.” The rules for reading them, such as HTML semantics, CSS styling, and JavaScript behavior, belong to “Structure & Semantics.” Once interpreted, they become usable page elements, such as text, buttons, forms, links, images, and layout containers, which belong to “Components, Controls, & Layouts.” The document and DOM then provide “Graphs & Frames,” organizing those elements into a current interface context. From there, the browser’s “Renderer” prepares the page for presentation. The browser appears inside a “Window” provided by the operating system, which then serves as the “System” that delivers the result to the “Human Interface.”

### The Need for Connectors

During the early development of CatalystUI, we believed the Stack alone might be enough to describe a user interface. At first, this seemed reasonable. The Stack already provides a clearer, more complete way to identify each part in a user interface than many existing models do. But as we began using it as the foundation for real development, something still felt missing. We could describe _what_ each piece was. We could describe _where_ it belonged. But there was still a gap between them: _how_ did data move between layers? The Stack gave us the path, but it did not yet explain the movement from one layer to the next. To complete the Model, we needed to define those transitions. This is when “Connectors” become not merely an additional concept, but a necessity.
