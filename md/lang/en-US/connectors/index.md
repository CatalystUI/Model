# 6. Connectors

## High-Level Overview

Connectors are unique because they do more than describe _how_ information moves between layers; they also allow us to _abstract_ many of the limitations imposed by hardware devices. We are aware this is a bold claim, however, when a user interface is appropriately designed around the CatalystUI Stack, connectors can be built in such a way that they can be swapped out with different implementations as needed. In this sense, connectors act as a _translation medium for information_. Unlike the layers in the Stack, which are typically locked to a specific domain once assigned, connectors can transform information from one domain to another. For example, a connector could take stored text and prepare it for a screen, a speaker, or even tactile feedback through a braille display!

In the same way we identified each layer in the Stack, we can pinpoint our connectors by determining where one layer needs to communicate with another. This is an important distinction: unlike “Data Storage” and the “Human Interface,” connectors do not have implied endpoints. Instead, they are the mechanism that allows two neighboring layers to work together. Because of this, each connector is defined by the two explicit layers it sits between and the kind of communication it must support.

### The Connectors of the Stack

At the top of the Stack, the first required connection sits between Layer 7, “Digital Data,” and Layer 6, “Structure & Semantics.” Digital Data can hold the original material, such as a file, document, response, or database result, but the next layer needs to know how that material should be read. This means the connector between them must bring the stored content into the Model while preserving its format and meaning. A JSON settings file, for example, may begin as stored text, but it must be read as JSON before the interface can know what settings are available. Since this connector converts digital content into a structured format, we can classify it as a “Data” connector.

Once that content has been read into a meaningful structure, the next connection appears between Layer 6, “Structure & Semantics,” and Layer 5, “Components, Controls, & Layouts.” Layer 6 can explain what the content means, but Layer 5 still needs to know what usable parts should be created from it. In other words, this connector must turn an “instruction” into “reality.” If a page description says there should be a button, the next step is not merely _knowing_ that the button exists; the interface must _create_ the button as a working control. Since this connector _parses_ structures into usable interface parts, it seems appropriate to identify it as a “Parser” connector.

Once those usable parts are in place, the next connection is between Layer 5, “Components, Controls, & Layouts,” and Layer 4, “Graphs & Frames.” Layer 5 can describe what the interface contains and how those parts should behave, but Layer 4 needs that information organized into a larger context. This means the connector between them must take interface parts and place them into relationships that can be tracked, coordinated, and prepared for the next stage. A button, for example, may already exist as a control, but it still needs a position, size, state, and relationship to the surrounding frame before the rest of the interface can treat it as part of a complete scene. Since this connector _adapts_ usable interface parts into graph and frame structures, we can identify it as an “Adapter” connector.

From there, the organized frame must communicate with Layer 3, “Renderers,” through a connection to Layer 4, “Graphs & Frames.” Layer 4 can describe what exists in the interface and how each part relates to the whole, but Layer 3 needs instructions that it can produce. This means the connector between them must translate the organized scene into work suited for a specific rendering system. In a visual interface, a button inside a frame may need to be converted into rectangles, textures, glyphs, or draw commands before it can appear on screen. Since this connector _bridges_ the organized interface and the renderer that produces it, we can identify it as a “Bridge” connector.

After the renderer has prepared its work, the next connection appears between Layer 3, “Renderers,” and Layer 2, “Windows.” Layer 3 may know how to draw, play, or otherwise produce something, but it still needs a target to where that work can be delivered. Layer 2 provides the view through which the user receives it, so the connector between them must expose a usable place for the renderer to send its result. OpenGL, for example, can draw a scene, but it needs a place to put it before the image can appear to the user. Since this connector provides the _surface_ where rendered work meets the window, we can identify it as a “Surface” connector.

Finally, the bottom of the Stack requires communication between Layer 2, “Windows,” and Layer 1, “Systems.” At this point, the connector must work in whatever form Layer 1 naturally understands, whether that means an operating-system handle, a platform API, a device signal, or a physical mechanism. In a desktop application, this may be the native handle used to create and manage Layer 2. In an automatic door, it may be the built-in sensor and motor connection that lets the doorway respond. Since this connector communicates with the system in its own _native_ form, we’ll identify it as a “Native” connector.

### The Role of Connectors in the Model

With each connector now identified, we can describe the movement of the Model more completely. From top to bottom, the connectors are “Data,” “Parser,” “Adapter,” “Bridge,” “Surface,” and “Native.” Each one sits between two explicit layers of the Stack and explains how those layers communicate. The Data connector brings stored content into a structure the Model can understand. The Parser connector turns that structure into usable interface parts. The Adapter connector places those parts into graphs and frames. The Bridge connector prepares those organized structures for the renderer. The Surface connector gives the renderer a place to deliver its result. Finally, the Native connector allows the window to communicate with the system in the system’s own terms.

### Connectors and the Living Exchange

Together, these connectors complete the path described by the Stack. The layers tell us where information at is in the flow, while the connectors tell us how it moves from one step to the next. This is what allows the CatalystUI Model to describe more than a static arrangement of parts. It describes a living exchange: stored content becomes structure, structure becomes interface, interface becomes output, output reaches the user, and the user’s response can travel back through the same pattern. Because connectors can be replaced or reworked without redefining the layers themselves, they also give the Model one of its most important strengths: the ability to adapt to different devices, domains, and systems while preserving the same underlying flow of information.
