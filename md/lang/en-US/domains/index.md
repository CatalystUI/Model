# 4. Domains

## High-Level Overview

To describe the CatalystUI Model, we must first begin with domains. A _domain_ describes the category of data being handled during an interaction. It is the first step in breaking down the flow of information. It identifies what _kind_ of information the system is working with. A storefront door sensor may use visual or spatial cues to detect motion. A game controller could use tactile information to produce haptic feedback. A smart speaker might work with auditory information when processing speech. In almost all cases, the domains align with how people sense the world. The Model also accounts for data before it reaches a specific sense, as well as data that spans multiple senses simultaneously. As a result, the seven domains are defined as “symbolic,” “visual,” “auditory,” “tactile,” “olfactory,” “gustatory,” and “multisensory.”

Domains are useful because they make the flow of information easier to recognize, diagnose, and shape around the user’s needs. By identifying which domain the information belongs to, we can more clearly see what the system is doing, what it is not doing, and which parts of the user’s experience may be missing. This is especially important for accessibility: if an interface communicates only visually, the Model helps us recognize that tactile, auditory, or other forms of information may also need to be considered. Because domains describe how information participates in the user’s experience, classifying data into a domain must first start by asking what role it plays in the interaction. If data is meant to be seen, it is visual; if it is meant to be heard, it is auditory; if it is meant to be felt, it is tactile. If the data has not yet been committed to a specific sense, as is the case with a text file, it is symbolic. If multiple sensory categories work together as one experience, such as a video game combining visuals, sound, and controller vibration, it is multisensory.

## The Role of Domains in the Model

Once data has been classified into a domain, the interaction has a clearer starting point. We know what information the system handles, what experience the user will have, and whether other forms of communication need to be considered. With that category established, the Model can move from identifying the type of data to describing how it moves through the interface itself.
