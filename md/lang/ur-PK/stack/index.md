# 5. The Stack

## Per-Topic Summary

جب ہم یہ classify کر لیتے ہیں کہ flow میں _کس type_ کا data شامل ہے، تو اگلا سوال یہ ہوتا ہے کہ data _کہاں_ located ہے۔ existing solutions کا analysis یہاں بہت useful ہو جاتا ہے، خاص طور پر جب ہم ان کے differences دیکھتے ہیں۔ کسی بھی solution کو dissect کرنے سے پہلے، ہم دو fundamental truths identify کر سکتے ہیں: پہلی، _data_ کہیں نہ کہیں exist کرتا ہے، چاہے binary کے طور پر، disk پر، memory میں، یا کسی بھی data storage form میں؛ دوسری، _person_ بھی کہیں نہ کہیں exist کرتا ہے، چاہے screen، headphones، controller، یا کسی اور interface کے دوسری طرف۔ ہم ان دو concepts کو sandwich کی طرح دیکھیں گے: “Data Storage” اوپر کا bun، اور “Human Interface” نیچے کا bun۔ چونکہ identify کرنے کے بعد یہ دونوں information flow کے obvious parts ہیں، انہیں _implied_ کہا جائے گا، کیونکہ flow کی nature ان کی existence کو _imply_ کرتی ہے۔

### Stack کی Layers

Human Interface سے شروع کرتے ہوئے، ہم Stack کا پہلا layer اور major pattern identify کر سکتے ہیں: “system” کی موجودگی۔ system information کو ultimately user تک deliver کرنے کے طریقے کو organize کرتا ہے۔ most modern computers میں یہ role “operating system” (“OS”) ادا کرتا ہے، جو hardware اور software کے درمیان gap bridge کرتا ہے۔ form کچھ بھی ہو، ہر information flow میں ایک system ہونا چاہیے جو interface کے internal work کو user کے experience سے connect کرنے والا final step complete کرے۔

system useful ہونے کے لیے user کو اس کے ساتھ interact کرنے کا کوئی طریقہ چاہیے۔ “graphical user interface” (“GUI”) میں یہ عموماً window کے ذریعے ہوتا ہے۔ لیکن CatalystUI Model “graphical window” کو narrow سمجھتا ہے، کیونکہ ہر interface graphical نہیں ہوتا۔ اس کے بجائے Stack کا next layer، “window”، Layer 2 کے طور پر define کیا جاتا ہے، اور system میں کسی بھی “view” پر مشتمل ہوتا ہے۔ یہ traditional application window، command-line interface، visual terminal، audio-capture device، یا کوئی بھی context ہو سکتا ہے جہاں user system کو input دے یا output receive کرے۔

information کو window میں flow کرنے کے لیے “renderer” کی ضرورت ہوتی ہے، جو interface کی internal form اور user کی perceivable form کے درمیان data transform کرتا ہے؛ یہ Layer 3 ہے۔ GUI میں یہ اکثر OpenGL یا Vulkan جیسی library کے طور پر آتا ہے جو visual data کو window کے ذریعے display ہونے والے output میں convert کرتی ہے۔ renderers graphics تک limited نہیں۔ OpenAL، WASAPI، ASIO، یا CoreAudio جیسے audio renderers sound produce کر سکتے ہیں، جبکہ haptic renderers tactile feedback produce کر سکتے ہیں۔ interactions اکثر کم modification کے ساتھ pass ہوتے ہیں، مگر کبھی reinterpret یا redefine بھی ہو سکتے ہیں، جیسے infrared sensor سے motion data process کرنا۔ domain کچھ بھی ہو، renderer interface کے prepared data اور output کے لیے domain-specific form کے درمیان information convert کرتا ہے۔

renderer کے بعد layers کا ایک set آتا ہے جو interface کے اندر data کو organize اور track کرتا ہے۔ شروع میں یہ layers distinguish کرنا مشکل ہو سکتا ہے، مگر جب ہم دیکھتے ہیں کہ ہر layer کیا provide کرتی ہے تو بات clear ہو جاتی ہے۔ پہلے Layer 4: “Graphs & Frames” ہے۔ CatalystUI Model میں “graph” interface objects کے organized relationships کو represent کرتا ہے، جیسے 3D world میں object، component tree، یا interface کا subsection۔ “frame” larger current context represent کرتا ہے جو available graphs کو contain اور coordinate کرتا ہے، انہیں renderer کے لیے prepare کرتا ہے۔ web پر familiar example ہے: “Document Object Model” (“DOM”) webpage elements کو graph کی طرح organize کرتا ہے، جبکہ document itself وہ larger frame provide کرتا ہے جس میں یہ elements exist کرتے ہیں۔

چونکہ یہ form of information renderer-facing preparation کے لیے organized ہے، direct user interpretation کے لیے نہیں، اس لیے ہمیں ایک layer introduce کرنا ہوتی ہے جو data کو logical form میں separate کرے تاکہ اسے recognize، organize، یا interact کیا جا سکے۔ یہی Layer 5: “Components, Controls, & Layouts” ہے، جہاں زیادہ تر interaction processing ہوتی ہے۔ “component” interface کا کوئی بھی logical, usable part ہے، جیسے image، label، audio track، style element، یا کوئی object جو system present یا organize کر سکتا ہے۔ “control” interactions process کرتا ہے، جیسے button، toggle switch، slider، یا variable input۔ “layout” دوسرے components یا controls کو arrange کر کے meaningful order میں رکھتا ہے۔ graphical interface میں یہ distinctions visual elements، clickable controls، اور rows/columns کے طور پر appear ہو سکتی ہیں۔ مگر یہی pattern graphics سے باہر بھی apply ہوتا ہے: audio interface tracks یا sound effects کو components کے طور پر، انہیں play/adjust کرنے والے controls کے طور پر، اور groups میں organize کرنے والے layouts کے طور پر استعمال کر سکتا ہے۔ یہ layer essential ہے کیونکہ یہ interface کی usable structure represent کرتا ہے: parts that exist، parts that can respond، اور وہ arrangement جو graphs میں organize اور rendering کے لیے prepare ہونے سے پہلے موجود ہوتی ہے۔

interface کے logical parts کے پیچھے “Structure & Semantics”، Layer 6، ہے۔ یہ layer describe کرتی ہے کہ data کو components، controls، یا layouts بننے سے پہلے کیسے understood ہونا چاہیے۔ “Semantics” data پڑھنے کے rules define کرتے ہیں: اس کا meaning کیا ہے، order کیا ہے، اور ہر part کیسے understood ہونا چاہیے۔ “Structure” ان rules کے apply ہونے کے بعد data کی organized form ہے۔ دوسرے لفظوں میں، یہ layer ایسے data کو meaningful shape دیتی ہے جو text، bytes، fields، یا records کے طور پر exist کر سکتا ہے۔ web پر loaded HTML digital data کے طور پر شروع ہوتا ہے، اور اس کے rules define کرتے ہیں کہ اسے کیسے interpret کیا جائے۔ parsed document structure original HTML پر rules apply کرنے کا organized result ہے۔

آخر میں ہم Stack کے top، Layer 7: “Digital Data”، تک پہنچتے ہیں۔ یہ layer data کو اس وقت represent کرتا ہے جب وہ active interface flow میں computer-readable form میں داخل ہو چکا ہو، مگر باقی Model نے اسے ابھی interpret، organize، یا present نہ کیا ہو۔ یہ file، document، stream، web response، یا similar representation ہو سکتا ہے۔ اس point پر اسے ابھی structure میں shaped نہیں کیا گیا اور نہ sensory domain assign ہوا ہے۔ text document مثلاً ابھی visual یا auditory نہیں ہے۔ یہ active text representation ہے جسے Stack بعد میں interpret کر سکتا ہے۔ Stack اسے screen پر display کرنے یا speaker کے ذریعے aloud read کرنے کا انتخاب کر سکتا ہے، اس طرح اسے domain assign کرتا ہے۔ Digital Data flow کا upper turning point ہے: interaction upward move کر کے stored ہونے والی چیز change کر سکتا ہے، اور stored content بعد میں Stack میں واپس نیچے آ کر user experience کا حصہ بن سکتا ہے۔

### Model میں Stack کا کردار

اب جب Stack کا ہر piece identify ہو گیا، ہم Model کو as a whole describe کر سکتے ہیں۔ top سے bottom تک Stack “Data Storage” (implied)، “Digital Data”، “Structure & Semantics”، “Components, Controls, & Layouts”، “Graphs & Frames”، “Renderers”، “Windows”، “Systems”، اور “Human Interface” (implied) پر مشتمل ہے۔ سات explicit layers bottom-up numbered ہیں، “Systems” Layer One ہے اور “Digital Data” Layer Seven ہے۔ implied layers numbering سے باہر رہتی ہیں اور flow کے endpoints کے طور پر serve کرتی ہیں۔ Together یہ interface کے ذریعے information flow trace کرنے کا complete way دیتی ہیں۔ ہم پوچھ سکتے ہیں کہ کوئی چیز process میں کہاں ہے، کیا role serve کر رہی ہے، اور completed interaction میں کیسے contribute کرتی ہے۔ چونکہ Stack exact implementation کے بجائے pattern describe کرتا ہے، ہمیں system کی every internal detail جاننے کی ضرورت نہیں ہوتی۔ یہی Model کو powerful بناتا ہے، خاص طور پر ایسے دور میں جہاں large-language models، machine-learning systems، اور “AI”-driven architectures interface کے inner workings کو دیکھنا مشکل بنا سکتے ہیں۔

### Stack کی Demonstration

#### Door Sensor

اس کو demonstrate کرنے کے لیے door sensor example پر واپس آتے ہیں۔ پہلے ہم نے exchange کو یوں summarize کیا تھا: user آگے کا راستہ دیکھتا ہے، detection area میں داخل ہوتا ہے، system door کھولتا ہے، اور user کے گزرنے اور door بند ہونے کے بعد cycle ختم ہوتی ہے۔ Stack ہمیں exact hardware design جانے بغیر اسی process کو زیادہ detail میں describe کرنے دیتا ہے۔

action “Human Interface” پر شروع ہوتا ہے، جہاں user doorway کی طرف بڑھتا ہے، اور “System” تک پہنچتا ہے، جیسے controller، wiring، power source، اور motor assembly۔ system doorway hardware کے ذریعے physical signal receive کرتا ہے۔ “Window” اس signal کو doorway کے detection context سے associate کرتی ہے، جبکہ “Renderer” اسے usable event میں convert یا map کرتا ہے۔ “Graphs & Frames” event کو larger doorway context میں place کرتا ہے، جس میں detection area اور current door state شامل ہیں۔ “Components, Controls, & Layouts” decision خود handle کرتا ہے، یعنی door open، remain open، یا close ہونا چاہیے۔ یہ decision کرنے کے لیے control “Structure & Semantics” پر rely کر سکتا ہے، جیسے configuration format جو sensitivity یا delay timing settings کی location specify کرتا ہے۔ پھر وہ settings اور state changes “Digital Data” کے طور پر represent ہوتے ہیں، اور اگر retain کرنا ہو تو “Data Storage” میں رکھے جاتے ہیں۔

جب decision ہو جائے تو flow واپس Stack میں نیچے آتا ہے: updated door state interpret ہوتی ہے، control action میں بدلتی ہے، doorway context میں واپس place ہوتی ہے، “Renderer” اسے hardware کے قابل عمل form میں convert کرتا ہے، doorway mechanism کی “Window” سے گزرتی ہے، “System” اسے carry out کرتا ہے، اور آخر میں “Human Interface” اسے receive کرتا ہے۔ user door کو کھلتا دیکھتا ہے اور اندر سے گزر جاتا ہے۔

#### Web

دوسری example web ہے۔ web existing systems میں سے ایک ہے جو CatalystUI Stack سے بہت close map ہوتی ہے۔ HTML، CSS، JavaScript، network responses، browser engines، DOM trees، renderers، windows، اور operating systems سب information flow کے clear stages دکھاتے ہیں۔ webpage شروع میں stored یا transmitted data ہو سکتا ہے۔ browser اسے digital data کے طور پر receive کرتا ہے، structure اور semantics کے rules کے مطابق parse کرتا ہے، components اور controls بناتا ہے، DOM اور related graphs میں organize کرتا ہے، rendering engine کے ذریعے visual output prepare کرتا ہے، browser window کے اندر display کرتا ہے، اور operating system/hardware کے ذریعے user تک پہنچاتا ہے۔ user click، type، scroll، یا gesture کرتا ہے تو same flow reverse direction میں travel کر سکتا ہے۔

یہ demonstration دکھاتی ہے کہ Stack کسی single technology کو copy نہیں کرتا۔ web صرف ایک familiar example ہے۔ یہی pattern audio systems، games، embedded devices، physical access systems، command-line tools، and future interfaces میں بھی apply ہو سکتا ہے۔ Stack implementation کا نام نہیں؛ یہ information کی location اور role کا description ہے۔
