# 4.3 Domains :: Auditory

## 深入讨论

在 visual domain 之后，**auditory** domain 描述的是被塑造成可供听觉感知的数据。听觉数据是为了通过声音被感知而存在的信息：口语、音乐、警报、提示音，或任何其他用户通过聆听来理解的输出。visual data 把意义组织成可由视觉读取的形式，而 auditory data 则把意义组织成基于时间展开的声音。

这使 auditory domain 与 visual domain 有一个重要区别。视觉信息通常可以一次性扫视，但听觉信息通常会随着时间展开。用户可以看一眼屏幕并立刻识别多个关系，但声音必须按顺序被听见。因此，auditory data 很大程度上依赖时机、顺序、持续时间和节奏。意义不仅在于听到了什么，也在于什么时候听到，以及它如何变化。

一个存储的音频文件并不会仅仅因为包含声音数据就变成 auditory。只要它仍然处于存储、编码或抽象表示状态，它仍然是 symbolic。当系统把它产生为可感知的声音时，它才变成 auditory。由屏幕阅读器朗读的书面文本、被转换成提示音的通知，或通过音乐表达的游戏事件也是如此。在每种情况下，系统都把信息取出，并将它绑定到听觉。

### 理解听觉数据

理解听觉数据的一个有用方式，是考虑 **内容**、**时机** 和 **音调**。它们不是模型中的正式类别，但有助于解释声音如何以不同于视觉的方式承载意义。

**内容** 描述声音传达了什么。在语音输出中，它可能是正在朗读的词语。在音乐中，它可能是旋律、和声或进行。在通知中，它可能是告诉用户某件事已经发生的可识别模式。听觉内容是用户被期待去听见并理解的实质。

**时机** 描述声音什么时候发生，以及持续多久。警告音播放得太晚可能会失去作用。语音消息移动得太快可能会变得难以跟随。立即响应用户动作的音乐可能让体验感觉连贯，而延迟的声音可能让系统感觉脱节。时机很重要，因为听觉数据是在运动中被体验的。

**音调** 描述声音的品质或性格。柔和的提示声、尖锐的蜂鸣声和平静的语音，即使都是短暂的听觉信号，也可以传达非常不同的意义。音调帮助用户理解紧迫性、情绪、确认、警告或完成。它赋予声音情感和实践上的性格。

### 听觉意义

听觉输出通过声音表达意义，但声音本身不应被误认为完整意义。警告蜂鸣声可以传达一个问题，但蜂鸣声不是问题本身。语音标签可以传达文本，但声音不是底层结构。音乐提示可以传达成功、危险或转场，但意义来自系统如何在体验中使用这个提示。

这种区分很重要，因为声音可以很有力量，却不一定精确。一个短音可以吸引用户注意，但它可能无法解释发生了什么。语音消息可以解释得很清楚，但它可能比视觉提示花费更长时间。音乐可以塑造体验的感受，但它可能无法传达精确指令。当声音与系统需要表达的意义类型相匹配时，听觉设计才最强。

听觉数据对用户的影响也不同于视觉数据，因为声音可以在不要求用户直接看向系统的情况下到达用户。计时器可以从另一个房间响起。导航应用可以在用户眼睛仍然看路时发出语音。屏幕阅读器可以让用户在不依赖视觉的情况下操作软件。这使 auditory domain 在注意力被分散、视觉不可用，或声音是最清晰沟通路径时尤其有价值。

### 听觉数据与无障碍

auditory domain 对无障碍至关重要，因为它可以承载原本可能被困在视觉中的信息。文本可以被朗读。界面状态可以被宣布。导航可以通过声音引导。对于一些用户来说，听觉输出不是增强功能；它是系统变得可用的主要方式。

与此同时，当听觉信息是意义被传达的唯一方式时，它也可能产生无障碍问题。只以声音存在的警告可能被失聪或听力受限的用户错过。语音指令在嘈杂环境中可能难以跟随。声音效果可以确认某个动作，但如果没有另一种表示这种确认的方式，意义就会只依赖听觉。

这正是 domains 帮助揭示系统实际在做什么的地方。如果重要意义只通过声音承载，开发者可以询问它是否也应该以 symbolic、visual、tactile 或另一种形式提供。目标不是削弱听觉设计，而是在用户实际感知系统的不同方式之间保留意义。

### 更广泛体验中的听觉数据

听觉数据经常与其他 domains 一起工作。在视频播放器中，声音可能承载语音或音乐，而视觉承载运动。在游戏中，音频可能传达距离、危险、氛围或反馈。在操作系统中，声音可能支持通知、错误和确认。在每种情况下，auditory domain 都识别体验中被塑造成可供听觉感知的部分。

当声音与其他感知形式整合时，它可以成为更大 multisensory exchange 的一部分。与视觉动画配对的声音可以让动作感觉完成。与地图配对的语音方向可以比任一形式单独使用时更清楚地引导用户。与提示音配对的振动可以让通知更不容易被错过。听觉部分仍然有自己的角色，但完整体验可能取决于这些 domains 如何协同工作。

简而言之，auditory domain 描述的是被塑造成可听输出的信息。它帮助解释系统如何使用声音来传达内容、时机、音调和反馈。当听觉数据被妥善处理时，用户可以听见系统正在呈现什么，识别发生了什么变化，并在不需要体验的每个部分都可见的情况下作出回应。
