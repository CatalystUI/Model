# 5.6 The Stack :: Renderers

## Докладне обговорення

### Перетворювальний шар

**Renderers** — це шар, де організований стан інтерфейсу перетворюється на форму, готову до output. Layer 4 надає graphs і frames: підготовлений операційний контекст, який описує, що має бути надіслане вниз, як воно організоване і який поточний стан має бути представлений. Layer 3 отримує цей підготовлений контекст і перетворює його на форму, придатну для доставки через window і зрештою через system.

Цей шар називається rendering, бо виконує активне перетворення з представлення інтерфейсу на сприйманий output. Renderer не просто зберігає інтерфейс, інтерпретує його початковий вміст або керує зв’язками components. Його відповідальність — взяти підготовлений результат верхніх шарів і створити domain-specific output, потрібний нижчим шарам Stack.

### Rendering як перетворення

У CatalystUI rendering не обмежується графікою. Visual renderer може перетворювати підготовлений стан інтерфейсу на pixels, draw commands, textures, glyphs або інший visual output. Auditory renderer може перетворювати підготовлений стан на waveforms, samples, tracks або змішаний audio output. Tactile renderer може перетворювати підготовлений стан на haptic patterns. Конкретний домен може змінюватися, але роль шару залишається тією самою: rendering перетворює організоване представлення інтерфейсу на output, який system може доставити.

Ця відмінність робить Модель ширшою за традиційне мислення про graphical user interface. Renderer визначається не тим, чи малює він на екран. Він визначається тим, чи перетворює підготовлений стан інтерфейсу на нижчерівневу форму output. Результат може зрештою бути побачений, почутий, відчутий або інакше сприйнятий, але на Layer 3 у центрі саме перетворення.

### Відношення до Graphs & Frames

Renderers залежать від **Graphs & Frames**, бо не мають відповідати за розуміння всієї моделі інтерфейсу. Layer 4 розв’язує поточний операційний контекст, організовує components, готує межі, визначає релевантний стан і надає frame, придатний для rendering. Layer 3 потім перетворює цей підготовлений frame на форму, готову до output.

Це розділення важливе, бо організація і rendering — різні відповідальності. Graph може знати, як components співвідносяться між собою, а frame може знати, що має містити поточний прохід. Renderer має знати, як перетворити цей підготовлений контекст на відповідне представлення output. Коли ці відповідальності залишаються розділеними, renderer може залишатися спеціалізованим і ефективним, не стаючи глобальним керівником інтерфейсу.

### Відношення до Windows

Renderers також залежать від **Layer 2: Windows**, бо відрендерений output потребує цілі доставки. Renderer може створювати commands, buffers, streams або інші output-ready представлення, але цим результатам усе одно потрібно кудись потрапити. Window надає обмежений view, channel або delivery surface, через який відрендерений output може бути перенесений до system.

Це робить renderer активною точкою перетворення між верхньою моделлю інтерфейсу і нижньою моделлю доставки. Вище нього Stack переважно стосується значення, придатності, організації й активного стану. Нижче нього Stack стосується передавання output через window і в system. Layer 3 стоїть між цими питаннями і перетворює одне на інше.

### Domain-Specific відповідальність

Renderers за природою domain-specific. Renderer має розуміти тип output, який створює, бо різні domains потребують різних форм перетворення. Visual output, auditory output, tactile output та інші сенсорні форми не мають однакових вимог до доставки, навіть якщо створюються з одного й того самого концептуального стану інтерфейсу.

Це не означає, що верхні шари потрібно переписувати для кожного domain. Одна із сильних сторін Stack у тому, що верхні шари можуть узгоджено описувати вміст, взаємодію, організацію і стан, дозволяючи renderers спеціалізуватися в точці, де domain-specific conversion стає необхідним. Renderer — це місце, де ця спеціалізація стає явною.

Один інтерфейс також може містити більше одного renderer, коли кілька форм output обробляються окремо. У таких випадках кожен renderer відповідає за перетворення, потрібне його власному domain, а навколишній Stack зберігає ширший потік взаємодії.

### Rendering і сприйманість

Renderer готує output для сприйняття, але не є самим сприйняттям. Користувач не сприймає renderer напряму. Renderer створює форму, яка може пройти через window і system, доки не стане сприйманою через пристрій, channel або фізичний output.

Ця відмінність важлива, бо rendering усе ще є частиною процесу перетворення на боці комп’ютера. Visual renderer може створити pixel data, але користувач сприймає світло від дисплея. Auditory renderer може створити audio samples, але користувач сприймає звук через динаміки або навушники. Layer 3 готує output; нижчі шари доставляють його.

### Роль у потоці згори вниз

У потоці згори вниз Renderers отримують підготовлений frame від Layer 4 і перетворюють його на output-ready форму. Це точка, де активна модель інтерфейсу починає залишати абстрактну організацію components і входити в конкретний шлях доставки system.

Renderer може перетворити component state на draw operations, audio buffers, haptic instructions або інше domain-specific representation. Після цього перетворення результат передається шару Window, який надає обмежений channel або view, через який system може доставити output.

### Роль у потоці знизу вгору

У потоці знизу вгору Renderers також можуть брати участь в інтерпретації або перетворенні деталей взаємодії до їх повернення верхнім шарам. Interaction може прийти від system через window у формі, яку потрібно скоригувати, перекласти, пов’язати з відрендереною областю або перетворити на представлення, яке graph і frame зможуть маршрутизувати.

Це не робить renderer фінальним обробником взаємодії. Ця відповідальність належить відповідному control у Layer 5. Однак, оскільки renderer розуміє, як інтерфейс було перетворено на output, він може надати потрібний контекст для зворотного відображення або зіставлення частини цього перетворення. Наприклад, він може допомогти пов’язати нижчерівневу взаємодію з відрендереною позицією, output region, timing point або domain-specific target до того, як Layer 4 маршрутизує її вгору.

### Чому шар важливий

Renderers не дають Stack трактувати output як прямий наслідок організованих об’єктів інтерфейсу. Frame може описувати, що має бути представлене, але не стає автоматично сприйманим output. Щось має перетворити цей підготовлений контекст на форму, яку нижчі шари можуть доставити. Layer 3 надає це перетворення.

Відокремлюючи Renderers і від Graphs & Frames, і від Windows, Модель зберігає чистий розподіл відповідальності. Graphs & Frames організовує поточний контекст інтерфейсу. Renderers перетворюють цей контекст на output-ready форму. Windows надає обмежений channel, через який цей output досягає system. Ця відмінність дозволяє CatalystUI описувати rendering у різних доменах, не зводячи rendering до графіки, не змушуючи windows виконувати перетворення і не вимагаючи від верхніх об’єктів інтерфейсу знати, як їх зрештою буде доставлено.
