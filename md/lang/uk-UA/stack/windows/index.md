# 5.7 The Stack :: Windows

## Докладне обговорення

### Шар обмеженої доставки

**Windows** — це шар, де відрендерений output отримує обмежений контекст доставки. Layer 3 перетворює підготовлений стан інтерфейсу на output-ready форму, але цьому output усе ще потрібне визначене місце, channel або view, через які system зможе його доставити. Layer 2 надає цю межу.

Window слід розуміти як логічний контекст доставки, а не просто як візуальну рамку на екрані. У графічному середовищі window зазвичай виглядає як видима область, керована операційною системою. Однак у Моделі це поняття ширше: window — це system-facing контекст, через який output може бути наданий, а interaction може бути отримана. Він визначає, де відрендерений результат належить усередині навколишньої системи.

### Погляд усередину системи

Window діє як погляд усередину system. Він не створює system і не замінює renderer. Натомість він надає обмежений контекст, де output renderer може бути пов’язаний із доставкою на рівні system. Ця межа може включати позицію, розмір, фокус, видимість, контекст пристрою, output channel або іншу форму області, визначеної system.

Це важливо, бо відрендерений output не існує для користувача ізольовано. Його потрібно кудись доставити. Renderer може створити visual commands, audio samples, haptic instructions або інший domain-specific output, але ці результати все одно мають бути пов’язані з контекстом, який system розпізнає. Window надає цей зв’язок.

У візуальних інтерфейсах це легко розпізнати, бо window може відповідати прямокутній області на дисплеї. В інших domains ту саму концептуальну роль може виконувати сесія командного рядка, audio output context, device channel, virtual viewport або інший обмежений system-facing interface. Визначальна ознака — не візуальний вигляд. Визначальна ознака в тому, що window надає межу доставки між відрендереним output і system.

### Відношення до Renderers

Windows отримують output від Renderers, але не виконують rendering самі. Rendering — це перетворення підготовленого стану інтерфейсу на output-ready форму. Windowing — це дія, яка дає цьому output обмежений системний контекст, через який він може бути доставлений.

Ця відмінність не дає Layer 2 поглинути відповідальності Layer 3. Renderer має вирішувати, як організований стан інтерфейсу стає output-ready. Window має надавати system-facing місце або channel, куди цей output можна надіслати. Renderer перетворює; window містить, отримує й пересилає.

Це також дозволяє різним renderers цілитися в різні типи window. Visual renderer може цілитися в graphical window, а auditory renderer — в audio output context. Конкретна реалізація може відрізнятися за system і domain, але шарова відповідальність залишається узгодженою.

### Відношення до System

Windows залежать від **Layer 1: Systems**, бо зазвичай створюються, керуються, обмежуються або розпізнаються навколишньою платформою. System може визначати, як створюються windows, як вони отримують input, як розкривають output channels, до яких ресурсів мають доступ і як взаємодіють із hardware або lower-level services.

Це не робить window тотожним system. System — це ширше operating environment, яке надає hardware access, device services, scheduling, permissions, drivers і platform behavior. Window — це обмежений логічний контекст усередині цього середовища. Це interface-facing контекст, який дозволяє відрендереному output і interaction проходити між Stack і system.

Відокремлюючи Windows від System, Модель уникає трактування кожної деталі платформи як частини межі інтерфейсу. Window представляє конкретний system-facing контекст, який використовує інтерфейс. System представляє ширше середовище, що робить цей контекст можливим.

### Доставка output

У потоці згори вниз window отримує output-ready representation від renderer і передає його до system. Це етап, де відрендерений output уже не просто підготовлений інтерфейсом; він призначений контексту доставки, який system може використати.

Window може керувати межами, фокусом, buffering, видимістю, станом channel або іншими умовами доставки залежно від domain і реалізації. Ці деталі впливають на те, як output рухається в system, але не змінюють головної ролі шару. Window надає межу, через яку відрендерений output може стати system output.

Після того як output проходить через window, system може перенести його до відповідного пристрою, сервісу або фізичного процесу, що дозволяє користувачеві його сприйняти. Тому window близький до сприйманості, але не є самим сприйняттям. Він залишається частиною потоку на боці комп’ютера.

### Вхід взаємодії

У потоці знизу вгору window — перший явний шар Stack, де interaction, надана system, стає доступною змодельованому інтерфейсу. System може виявити натискання клавіші, рух вказівника, touch event, сигнал пристрою, аудіокоманду або іншу форму input. Window отримує цю interaction у межах свого обмеженого контексту і пересилає її вгору для подальшої маршрутизації й обробки.

Це робить window центральним для interaction, бо він надає контекст дії. Interaction — це не лише те, що щось сталося, а й те, що воно сталося всередині конкретної system-facing межі. Фокус, позиція, час, джерело пристрою, channel або активний контекст можуть визначати, як решта Stack має зрозуміти й маршрутизувати interaction.

Window зазвичай не вирішує остаточне значення interaction. Ця відповідальність розташована вище в Stack, особливо коли interaction досягає відповідного control. Роль window — отримати interaction від system, пов’язати її з правильною межею і передати вгору у формі, яку решта Stack може продовжити обробляти.

### Незалежність від домену

Windows незалежні від domain так само, як і решта Stack. Слово “window” часто пов’язують із графікою, але в CatalystUI воно означає будь-який обмежений system-facing контекст для output і interaction. Domain визначає, який вид output і input несе window; положення в Stack визначає, яку роль window виконує.

Це дозволяє одному й тому самому шару описувати graphical windows, text sessions, audio channels, tactile output contexts або інші форми interface delivery без зміни Моделі. Кожна реалізація може мати різні system requirements, але кожна виконує одну й ту саму концептуальну відповідальність: надає межу, через яку проходять відрендерений output і system interaction.

### Чому шар важливий

Windows не дає Stack трактувати відрендерений output так, ніби він автоматично досягає користувача. Renderer може перетворити стан інтерфейсу на output-ready форму, але цьому output усе ще потрібен system-facing контекст. Layer 2 надає цей контекст.

Відокремлюючи Windows і від Renderers, і від System, Модель зберігає чистий шлях доставки. Renderers перетворюють підготовлений стан інтерфейсу на output-ready representation. Windows надає обмежений контекст, через який це представлення входить у system. System потім виконує нижчерівневу роботу, потрібну для доставки output і отримання input. Ця відмінність дозволяє CatalystUI описувати interface delivery на різних платформах і в різних доменах, не зводячи windows до візуальних прямокутників і не змушуючи renderers керувати platform-level behavior.
