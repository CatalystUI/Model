# 6. Connectors

## Visão geral de alto nível

Connectors são únicos porque fazem mais do que descrever _como_ a informação se move entre camadas; eles também nos permitem _abstrair_ muitas das limitações impostas por dispositivos de hardware. Sabemos que esta é uma afirmação ousada; no entanto, quando uma interface de usuário é projetada adequadamente em torno do Stack CatalystUI, os connectors podem ser construídos de tal forma que possam ser trocados por implementações diferentes conforme necessário. Nesse sentido, connectors atuam como um _meio de tradução para a informação_. Ao contrário das camadas do Stack, que normalmente ficam presas a um domínio específico depois de atribuídas, connectors podem transformar informação de um domínio para outro. Por exemplo, um connector poderia pegar texto armazenado e prepará-lo para uma tela, um alto-falante ou até feedback tátil por meio de uma linha braille!

Da mesma forma que identificamos cada camada do Stack, podemos localizar nossos connectors determinando onde uma camada precisa se comunicar com outra. Esta é uma distinção importante: ao contrário de “Data Storage” e da “Human Interface”, connectors não têm pontos finais implícitos. Em vez disso, eles são o mecanismo que permite que duas camadas vizinhas trabalhem juntas. Por isso, cada connector é definido pelas duas camadas explícitas entre as quais se posiciona e pelo tipo de comunicação que deve suportar.

### Os Connectors do Stack

No topo do Stack, a primeira conexão necessária fica entre Layer 7, “Digital Data”, e Layer 6, “Structure & Semantics”. Digital Data pode conter o material original, como um arquivo, documento, resposta ou resultado de banco de dados, mas a próxima camada precisa saber como esse material deve ser lido. Isso significa que o connector entre elas deve trazer o conteúdo armazenado para dentro do Modelo preservando seu formato e significado. Um arquivo de configurações JSON, por exemplo, pode começar como texto armazenado, mas precisa ser lido como JSON antes que a interface saiba quais configurações estão disponíveis. Como esse connector converte conteúdo digital em um formato estruturado, podemos classificá-lo como um connector “Data”.

Depois que esse conteúdo foi lido em uma estrutura significativa, a próxima conexão aparece entre Layer 6, “Structure & Semantics”, e Layer 5, “Components, Controls, & Layouts”. Layer 6 pode explicar o que o conteúdo significa, mas Layer 5 ainda precisa saber quais partes utilizáveis devem ser criadas a partir dele. Em outras palavras, esse connector precisa transformar uma “instrução” em “realidade”. Se uma descrição de página diz que deve haver um botão, o próximo passo não é apenas _saber_ que o botão existe; a interface precisa _criar_ o botão como um control funcional. Como esse connector _faz parsing_ de structures em partes utilizáveis da interface, parece apropriado identificá-lo como um connector “Parser”.

Depois que essas partes utilizáveis estão no lugar, a próxima conexão é entre Layer 5, “Components, Controls, & Layouts”, e Layer 4, “Graphs & Frames”. Layer 5 pode descrever o que a interface contém e como essas partes devem se comportar, mas Layer 4 precisa dessa informação organizada em um contexto maior. Isso significa que o connector entre elas deve pegar partes da interface e colocá-las em relações que possam ser rastreadas, coordenadas e preparadas para o próximo estágio. Um botão, por exemplo, pode já existir como control, mas ainda precisa de posição, tamanho, estado e relação com o frame ao redor antes que o restante da interface possa tratá-lo como parte de uma cena completa. Como esse connector _adapta_ partes utilizáveis da interface em estruturas de graph e frame, podemos identificá-lo como um connector “Adapter”.

A partir daí, o frame organizado deve se comunicar com Layer 3, “Renderers”, por meio de uma conexão com Layer 4, “Graphs & Frames”. Layer 4 pode descrever o que existe na interface e como cada parte se relaciona com o todo, mas Layer 3 precisa de instruções que possa produzir. Isso significa que o connector entre elas deve traduzir a cena organizada em trabalho adequado para um sistema de renderização específico. Em uma interface visual, um botão dentro de um frame pode precisar ser convertido em retângulos, texturas, glifos ou comandos de desenho antes de aparecer na tela. Como esse connector _faz a ponte_ entre a interface organizada e o renderer que a produz, podemos identificá-lo como um connector “Bridge”.

Depois que o renderer preparou seu trabalho, a próxima conexão aparece entre Layer 3, “Renderers”, e Layer 2, “Windows”. Layer 3 pode saber desenhar, tocar ou produzir algo de outra forma, mas ainda precisa de um destino para onde esse trabalho possa ser entregue. Layer 2 fornece a visão pela qual o usuário o recebe, então o connector entre elas deve expor um lugar utilizável para o renderer enviar seu resultado. OpenGL, por exemplo, pode desenhar uma cena, mas precisa de um lugar para colocá-la antes que a imagem possa aparecer para o usuário. Como esse connector fornece a _surface_ onde o trabalho renderizado encontra a window, podemos identificá-lo como um connector “Surface”.

Por fim, a parte inferior do Stack exige comunicação entre Layer 2, “Windows”, e Layer 1, “Systems”. Nesse ponto, o connector deve trabalhar em qualquer forma que Layer 1 entenda naturalmente, seja um handle do sistema operacional, uma API de plataforma, um sinal de dispositivo ou um mecanismo físico. Em uma aplicação desktop, pode ser o handle nativo usado para criar e gerenciar Layer 2. Em uma porta automática, pode ser a conexão embutida de sensor e motor que permite que a porta responda. Como esse connector se comunica com o sistema em sua forma _nativa_, vamos identificá-lo como um connector “Native”.

### O papel dos Connectors no Modelo

Com cada connector agora identificado, podemos descrever o movimento do Modelo de forma mais completa. De cima para baixo, os connectors são “Data”, “Parser”, “Adapter”, “Bridge”, “Surface” e “Native”. Cada um fica entre duas camadas explícitas do Stack e explica como essas camadas se comunicam. O connector Data traz conteúdo armazenado para uma estrutura que o Modelo pode entender. O connector Parser transforma essa estrutura em partes utilizáveis da interface. O connector Adapter coloca essas partes em graphs e frames. O connector Bridge prepara essas estruturas organizadas para o renderer. O connector Surface dá ao renderer um lugar para entregar seu resultado. Por fim, o connector Native permite que a window se comunique com o system nos próprios termos do system.

### Connectors e a troca viva

Juntos, esses connectors completam o caminho descrito pelo Stack. As camadas nos dizem onde a informação está no fluxo, enquanto os connectors nos dizem como ela se move de um passo para o próximo. É isso que permite ao Modelo CatalystUI descrever mais do que uma organização estática de partes. Ele descreve uma troca viva: conteúdo armazenado vira structure, structure vira interface, interface vira output, output chega ao usuário, e a resposta do usuário pode viajar de volta pelo mesmo padrão. Como connectors podem ser substituídos ou retrabalhados sem redefinir as próprias camadas, eles também dão ao Modelo uma de suas forças mais importantes: a capacidade de se adaptar a diferentes dispositivos, domínios e sistemas enquanto preserva o mesmo fluxo subjacente de informação.
