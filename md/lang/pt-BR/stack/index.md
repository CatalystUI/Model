# 5. O Stack

## Visão geral de alto nível

Depois de classificar _que_ tipo de dado está envolvido no fluxo, podemos nos concentrar em _onde_ esse dado está localizado. É aqui que analisar soluções existentes pode ser realmente útil, especialmente ao examinar suas diferenças. Antes de dissecar cada solução, podemos identificar duas verdades fundamentais para dar uma base sólida à nossa análise: primeiro, os _dados_ precisam existir em algum lugar, seja armazenados como binário, em disco, na memória ou em qualquer outra forma de armazenamento de dados; segundo, uma _pessoa_ também precisa existir em algum lugar, seja do outro lado de uma tela, fones de ouvido, controle ou qualquer outra forma de interface. Vamos ver esses dois conceitos como um sanduíche, com “Data Storage” como o pão de cima e “Human Interface” como o pão de baixo. Como esses dois conceitos são óbvios, uma vez identificados, como partes do fluxo de informação, vamos chamá-los de _implícitos_, já que a natureza do fluxo _implica_ sua existência.

### As camadas do Stack

Começando pela interface humana, podemos identificar a primeira camada e o primeiro grande padrão no Stack: a presença de um “sistema”. Um sistema é responsável por organizar como a informação será finalmente entregue ao usuário. Na maioria dos computadores modernos, esse papel é cumprido por um “sistema operacional” (“OS”), que faz a ponte entre o hardware e o software de um computador. Independentemente da forma, em qualquer fluxo de informação, um sistema deve existir para completar o passo final que conecta o trabalho interno da interface ao que o usuário experimenta.

Para que um sistema seja útil, o usuário precisa de alguma forma de interagir com ele. Em uma “interface gráfica de usuário” (“GUI”), isso normalmente é feito por uma janela. No entanto, o Modelo CatalystUI trata a ideia de uma “janela gráfica” como estreita demais, já que nem toda interface é gráfica. Em vez disso, a próxima camada do Stack, uma “window”, é definida como Layer 2 e consiste em qualquer “visão” para dentro de um sistema. Pode ser uma janela tradicional de aplicativo, uma interface de linha de comando, um terminal visual, um dispositivo de captura de áudio ou qualquer outro contexto no qual o usuário possa fornecer entrada ao sistema ou receber saída dele.

Para permitir que a informação flua para uma window, é necessário um “renderer” para transformar dados entre a forma interna usada pela interface e a forma perceptível usada pelo usuário, atuando como Layer 3. Em uma GUI, isso frequentemente aparece como uma biblioteca como OpenGL ou Vulkan, convertendo dados visuais em saída que pode ser exibida por uma janela. No entanto, renderers não se limitam a gráficos. Renderers de áudio, como OpenAL, WASAPI, ASIO ou CoreAudio, podem produzir som, enquanto renderers hápticos podem produzir feedback tátil. Na maioria dos casos, as interações passam com pouca modificação, mas podem ser reinterpretadas ou redefinidas, como no processamento de dados de movimento de um sensor infravermelho. Independentemente do domínio dos dados, o renderer é responsável por converter informação entre os dados preparados pela interface e a forma específica do domínio usada para saída.

Depois do renderer vem um conjunto de camadas que organizam e rastreiam dados dentro da interface. Essas camadas podem ser difíceis de distinguir no começo, mas ficam mais claras quando consideramos o que cada uma fornece, sendo a primeira Layer 4: “Graphs & Frames”. No Modelo CatalystUI, um “graph” representa uma estrutura organizada preparada para renderização, como um objeto em um mundo 3D, uma árvore de componentes ou uma subseção de uma interface. Um “frame” representa o contexto maior que contém e coordena os graphs disponíveis, preparando-os para serem passados ao renderer. Um exemplo familiar pode ser encontrado na web: o “Document Object Model” (“DOM”) organiza os elementos de uma página como um graph, enquanto o próprio documento fornece o frame maior no qual esses elementos existem.

Como essa forma de informação é otimizada para o renderer em vez da interpretação do usuário, precisamos introduzir uma camada que separa os dados em sua forma lógica para serem reconhecidos, organizados ou usados em interação. É aqui que ocorre a maior parte do processamento de interações; por isso, o Modelo CatalystUI se refere à Layer 5 como “Components, Controls, & Layouts”. Um “component” é qualquer parte lógica da interface, como uma imagem, rótulo, faixa de áudio, elemento de estilo ou outro objeto que o sistema possa apresentar ou organizar. Um “control” processa interações, como um botão, chave, slider ou entrada variável. Um “layout” organiza outros components ou controls e os coloca em uma ordem significativa. Em uma interface gráfica, essas distinções podem aparecer como elementos visuais, controls clicáveis e linhas ou colunas. Porém, o mesmo padrão também se aplica fora dos gráficos: uma interface de áudio pode usar components para representar faixas ou efeitos sonoros, controls para reproduzi-los ou ajustá-los, e layouts para organizá-los em grupos. Essa camada é essencial porque representa a estrutura utilizável da interface: as partes que existem, as partes que podem responder e a forma como essas partes são organizadas antes de serem colocadas em graphs e preparadas para renderização.

Sustentando as partes lógicas da interface está “Structure & Semantics”, Layer 6. Essa camada descreve como os dados devem ser entendidos antes de se tornarem components, controls ou layouts. “Semantics” define as regras para ler os dados: o que significam, a ordem que seguem e como cada parte deve ser entendida. “Structure” é a forma organizada desses dados depois que essas regras foram aplicadas. Em outras palavras, essa camada pega dados que talvez existam apenas como texto, bytes, campos ou registros e lhes dá uma forma significativa que o restante da interface pode usar. Na web, por exemplo, HTML carregado começa como Digital Data, e suas regras definem como deve ser interpretado. A estrutura do documento analisado é o resultado organizado da aplicação dessas regras ao HTML original.

Por fim, chegamos ao topo do Stack, Layer 7: “Digital Data” em si. Essa camada representa dados antes que o restante do Modelo os tenha lido, organizado ou apresentado. É um arquivo, documento, stream, resposta web ou outra representação semelhante. Nesse ponto, ainda não foi moldado em uma structure nem atribuído a um domínio sensorial. Um documento de texto, por exemplo, ainda não é visual nem auditivo. É simplesmente texto armazenado. O Stack pode depois escolher exibi-lo em uma tela ou lê-lo em voz alta por um alto-falante, atribuindo-o então a um domínio. Digital Data é, portanto, o ponto de virada superior do fluxo: uma interação pode subir e mudar o que está armazenado, e o que está armazenado pode depois descer novamente pelo Stack para se tornar parte da experiência do usuário.

### O papel do Stack no Modelo

Com cada parte do Stack agora identificada, podemos descrever o Modelo como um todo. De cima para baixo, o Stack consiste em “Data Storage” (implícito), “Digital Data”, “Structure & Semantics”, “Components, Controls, & Layouts”, “Graphs & Frames”, “Renderers”, “Windows”, “Systems” e a “Human Interface” (implícita). As sete camadas explícitas são numeradas de baixo para cima, com “Systems” como Layer One e “Digital Data” como Layer Seven. As camadas implícitas ficam fora dessa numeração e servem como pontos finais do fluxo. Juntas, elas nos dão uma forma completa de rastrear o fluxo de informação através de uma interface. Elas nos permitem perguntar onde algo está no processo, que papel está cumprindo e como contribui para a conclusão da interação. Como o Stack descreve o padrão em vez de uma implementação exata, não precisamos conhecer cada detalhe interno de um sistema para começar a entendê-lo. Isso é parte do que torna o Modelo poderoso, especialmente em uma era em que grandes modelos de linguagem, sistemas de machine learning e outras formas de arquitetura movida por “IA” podem tornar mais difícil ver o funcionamento interno de uma interface.

### Demonstrando o Stack

#### Um sensor de porta

Para demonstrar isso, podemos voltar ao exemplo do sensor de porta. Antes, resumimos a troca assim: o usuário vê um caminho à frente, entra na área de detecção, o sistema abre a porta, e o ciclo termina quando o usuário passa e a porta fecha. O Stack nos permite descrever esse mesmo processo com mais detalhe sem conhecer o design exato do hardware.

A ação começa na “Human Interface”, onde o usuário se aproxima da porta, e chega ao “System”, como um controlador, fiação, fonte de energia e conjunto de motor. A “Window” detecta a presença do usuário por meio de um sensor de movimento ou detector de calor, enquanto o “Renderer” converte esse sinal físico em um evento utilizável. “Graphs & Frames” coloca o evento no contexto maior da porta, incluindo a área de detecção e o estado atual da porta. “Components, Controls, & Layouts” lida com a decisão em si, determinando se a porta deve abrir, permanecer aberta ou fechar. Para tomar essa decisão, o control pode depender de “Structure & Semantics”, como um formato de configuração que especifica onde ficam configurações como sensibilidade ou tempo de atraso. Essas configurações e mudanças de estado são então representadas como “Digital Data” e, se precisarem ser mantidas, colocadas em “Data Storage”.

Depois que a decisão é tomada, o fluxo volta a descer pelo Stack: o estado atualizado da porta é interpretado, transformado em uma ação de control, colocado novamente no contexto da porta, convertido pelo “Renderer” em algo que o hardware pode executar, passado pela “Window” do mecanismo da porta, realizado pelo “System” e, por fim, recebido pela “Human Interface”. Finalmente, o usuário vê a porta abrir e passa por ela.

#### A Web

Como segundo exemplo, podemos olhar para a web. A web é uma das tentativas existentes mais próximas de um amplo modelo de interface de usuário, especialmente por meio do W3C e de suas interfaces padronizadas. No entanto, por ser projetada principalmente em torno da comunicação entre computadores, ela não captura sozinha cada parte do Stack. Em uma página web típica, “Data Storage” pode ser representado pelo servidor, banco de dados, sistema de arquivos ou API que hospeda a página. Quando o navegador busca HTML, CSS, JavaScript, imagens e recursos semelhantes, eles se tornam “Digital Data”. As regras para lê-los, como semântica HTML, estilo CSS e comportamento JavaScript, pertencem a “Structure & Semantics”. Depois de interpretados, tornam-se elementos de página utilizáveis, como texto, botões, formulários, links, imagens e contêineres de layout, que pertencem a “Components, Controls, & Layouts”. A página então é organizada em “Graphs & Frames”, anteriormente mencionado como Document Object Model. A partir daí, o “Renderer” do navegador prepara a página para apresentação. O navegador aparece dentro de uma “Window” fornecida pelo sistema operacional, que então serve como o “System” que entrega o resultado à “Human Interface”.

## A necessidade de Connectors

Durante o desenvolvimento inicial do CatalystUI, acreditávamos que o Stack sozinho poderia ser suficiente para descrever uma interface de usuário. No começo, isso parecia razoável. O Stack já oferece uma forma mais clara e completa de identificar cada parte em uma interface de usuário do que muitos modelos existentes. Mas, quando começamos a usá-lo como base para desenvolvimento real, algo ainda parecia faltar. Podíamos descrever _o que_ cada peça era. Podíamos descrever _onde_ ela pertencia. Mas ainda havia uma lacuna entre elas: _como_ os dados se moviam entre camadas? O Stack nos dava o caminho, mas ainda não explicava o movimento de uma camada para a próxima. Para completar o Modelo, precisávamos definir essas transições. É quando “Connectors” se tornam não apenas um conceito adicional, mas uma necessidade.
