# 5. El Stack

## Visión general de alto nivel

Después de clasificar _qué_ tipo de datos participa en el flujo, podemos centrarnos en _dónde_ se encuentran esos datos. Aquí es donde analizar soluciones existentes puede resultar realmente útil, especialmente al examinar sus diferencias. Antes de descomponer cada solución, podemos identificar dos verdades fundamentales que dan una base sólida a nuestro análisis: primero, los _datos_ deben existir en algún lugar, ya sea almacenados como binario, en un disco, en memoria o en cualquier otra forma de almacenamiento de datos; y segundo, una _persona_ también debe existir en algún lugar, ya sea al otro lado de una pantalla, unos auriculares, un mando o cualquier otra forma de interfaz. Veremos estos dos conceptos como un bocadillo, con “Data Storage” como el pan superior y “Human Interface” como el pan inferior. Como estos dos conceptos son obvios, una vez identificados, como partes del flujo de información, los llamaremos _implícitos_, ya que la naturaleza del flujo _implica_ su existencia.

### Las capas del Stack

Comenzando desde la interfaz humana, podemos identificar la primera capa y el primer patrón importante del Stack: la presencia de un “sistema”. Un sistema es responsable de organizar cómo se entrega finalmente la información al usuario. En la mayoría de los ordenadores modernos, este papel lo cumple un “sistema operativo” (“OS”), que salva la distancia entre el hardware y el software del ordenador. Independientemente de su forma, en cualquier flujo de información debe existir un sistema para completar el paso final que conecta el trabajo interno de la interfaz con lo que el usuario experimenta.

Para que un sistema sea útil, el usuario necesita alguna forma de interactuar con él. En una “interfaz gráfica de usuario” (“GUI”), esto suele hacerse mediante una ventana. Sin embargo, el Modelo CatalystUI trata la idea de una “ventana gráfica” como demasiado estrecha, ya que no toda interfaz es gráfica. En su lugar, la siguiente capa del Stack, una “window”, se define como Layer 2 y consiste en cualquier “vista” hacia un sistema. Puede ser una ventana tradicional de aplicación, una interfaz de línea de comandos, un terminal visual, un dispositivo de captura de audio o cualquier otro contexto en el que el usuario pueda proporcionar entrada al sistema o recibir salida de él.

Para permitir que la información fluya hacia una window, se necesita un “renderer” que transforme los datos entre la forma interna usada por la interfaz y la forma perceptible usada por el usuario, actuando como Layer 3. En una GUI, esto suele aparecer como una biblioteca como OpenGL o Vulkan, que convierte datos visuales en una salida que puede mostrarse a través de una ventana. Sin embargo, los renderers no se limitan a los gráficos. Renderers de audio como OpenAL, WASAPI, ASIO o CoreAudio pueden producir sonido, mientras que renderers hápticos pueden producir retroalimentación táctil. En la mayoría de los casos, las interacciones pasan con poca modificación, pero pueden reinterpretarse o redefinirse, como al procesar datos de movimiento de un sensor infrarrojo. Independientemente del dominio de los datos, el renderer es responsable de convertir información entre los datos preparados por la interfaz y la forma específica del dominio usada para la salida.

Después del renderer viene un conjunto de capas que organizan y rastrean datos dentro de la interfaz. Estas capas pueden ser difíciles de distinguir al principio, pero se vuelven más claras cuando consideramos qué proporciona cada una; la primera es Layer 4: “Graphs & Frames”. En el Modelo CatalystUI, un “graph” representa una estructura organizada preparada para renderizarse, como un objeto en un mundo 3D, un árbol de componentes o una subsección de una interfaz. Un “frame” representa el contexto mayor que contiene y coordina los graphs disponibles, preparándolos para pasarlos al renderer. Un ejemplo familiar se encuentra en la web: el “Document Object Model” (“DOM”) organiza los elementos de una página web como un graph, mientras que el documento mismo proporciona el frame mayor en el que esos elementos existen.

Como esta forma de información está optimizada para el renderer y no para la interpretación del usuario, necesitamos introducir una capa que separe los datos en su forma lógica para que puedan reconocerse, organizarse o usarse en interacción. Aquí ocurre la mayor parte del procesamiento de interacciones, por lo que el Modelo CatalystUI llama a Layer 5: “Components, Controls, & Layouts”. Un “component” es cualquier parte lógica de la interfaz, como una imagen, etiqueta, pista de audio, elemento de estilo u otro objeto que el sistema pueda presentar u organizar. Un “control” procesa interacciones, como un botón, interruptor, deslizador o entrada variable. Un “layout” organiza otros components o controls y los coloca en un orden significativo. En una interfaz gráfica, estas distinciones pueden aparecer como elementos visuales, controls clicables y filas o columnas. Sin embargo, el mismo patrón también se aplica fuera de los gráficos: una interfaz de audio puede usar components para representar pistas o efectos de sonido, controls para reproducirlos o ajustarlos, y layouts para organizarlos en grupos. Esta capa es esencial porque representa la estructura usable de la interfaz: las partes que existen, las partes que pueden responder y la forma en que esas partes se organizan antes de convertirse en graphs y prepararse para renderizar.

Respaldando las partes lógicas de la interfaz está “Structure & Semantics”, Layer 6. Esta capa describe cómo deben entenderse los datos antes de convertirse en components, controls o layouts. “Semantics” define las reglas para leer los datos: qué significan, qué orden siguen y cómo debe entenderse cada parte. “Structure” es la forma organizada de esos datos después de aplicar esas reglas. En otras palabras, esta capa toma datos que quizá existan solo como texto, bytes, campos o registros, y les da una forma significativa que el resto de la interfaz puede usar. En la web, por ejemplo, el HTML cargado comienza como Digital Data, y sus reglas definen cómo debe interpretarse. La estructura del documento parseado es el resultado organizado de aplicar esas reglas al HTML original.

Finalmente, llegamos a la parte superior del Stack, Layer 7: “Digital Data” en sí. Esta capa representa los datos antes de que el resto del Modelo los haya leído, organizado o presentado. Es un archivo, documento, flujo, respuesta web u otra representación similar. En este punto, aún no ha sido moldeado en una structure ni asignado a un dominio sensorial. Un documento de texto, por ejemplo, aún no es visual ni auditivo. Es simplemente texto almacenado. El Stack puede más tarde elegir mostrarlo en una pantalla o leerlo en voz alta mediante un altavoz, asignándolo así a un dominio. Digital Data es, por tanto, el punto de giro superior del flujo: una interacción puede moverse hacia arriba y cambiar lo que está almacenado, y lo almacenado puede luego volver a bajar por el Stack para convertirse en parte de la experiencia del usuario.

### El papel del Stack en el Modelo

Con cada pieza del Stack ya identificada, podemos describir el Modelo como un todo. De arriba abajo, el Stack consta de “Data Storage” (implícito), “Digital Data”, “Structure & Semantics”, “Components, Controls, & Layouts”, “Graphs & Frames”, “Renderers”, “Windows”, “Systems” y la “Human Interface” (implícita). Las siete capas explícitas se numeran desde abajo hacia arriba, con “Systems” como Layer One y “Digital Data” como Layer Seven. Las capas implícitas quedan fuera de esta numeración y sirven como extremos del flujo. Juntas nos dan una forma completa de rastrear el flujo de información a través de una interfaz. Nos permiten preguntar dónde está algo en el proceso, qué papel cumple y cómo contribuye a completar la interacción. Como el Stack describe el patrón en lugar de una implementación exacta, no necesitamos conocer cada detalle interno de un sistema para empezar a entenderlo. Esto es parte de lo que hace poderoso al Modelo, especialmente en una era en la que los modelos de lenguaje grandes, los sistemas de aprendizaje automático y otras formas de arquitectura impulsada por “IA” pueden hacer más difícil ver el funcionamiento interno de una interfaz.

### Demostrando el Stack

#### Un sensor de puerta

Para demostrarlo, podemos volver al ejemplo del sensor de puerta. Antes resumimos el intercambio así: el usuario ve un camino hacia delante, entra en el área de detección, el sistema abre la puerta, y el ciclo termina cuando el usuario pasa y la puerta se cierra. El Stack nos permite describir ese mismo proceso con más detalle sin conocer el diseño exacto del hardware.

La acción comienza en la “Human Interface”, donde el usuario se acerca a la puerta, y llega al “System”, como un controlador, cableado, fuente de alimentación y conjunto de motor. La “Window” detecta la presencia del usuario mediante un sensor de movimiento o detector de calor, mientras que el “Renderer” convierte esa señal física en un evento utilizable. “Graphs & Frames” coloca el evento dentro del contexto mayor de la puerta, incluyendo el área de detección y el estado actual de la puerta. “Components, Controls, & Layouts” maneja la decisión en sí, determinando si la puerta debe abrirse, permanecer abierta o cerrarse. Para tomar esa decisión, el control puede depender de “Structure & Semantics”, como un formato de configuración que especifique dónde se encuentran ajustes como sensibilidad o tiempo de retraso. Esos ajustes y cambios de estado se representan entonces como “Digital Data” y, si deben conservarse, se colocan en “Data Storage”.

Una vez tomada la decisión, el flujo vuelve a descender por el Stack: el estado actualizado de la puerta se interpreta, se convierte en una acción de control, se coloca de nuevo en el contexto de la puerta, el “Renderer” lo convierte en algo que el hardware puede ejecutar, pasa por la “Window” del mecanismo de la puerta, el “System” lo lleva a cabo, y finalmente lo recibe la “Human Interface”. Por último, el usuario ve abrirse la puerta y pasa a través de ella.

#### La Web

Como segundo ejemplo, podemos observar la web. La web es uno de los intentos existentes más cercanos a un modelo amplio de interfaz de usuario, especialmente a través del W3C y sus interfaces estandarizadas. Sin embargo, como está diseñada principalmente alrededor de la comunicación entre ordenadores, no captura por sí sola cada parte del Stack. En una página web típica, “Data Storage” puede estar representado por el servidor, la base de datos, el sistema de archivos o la API que aloja la página. Cuando el navegador obtiene HTML, CSS, JavaScript, imágenes y recursos similares, estos se convierten en “Digital Data”. Las reglas para leerlos, como la semántica HTML, el estilo CSS y el comportamiento JavaScript, pertenecen a “Structure & Semantics”. Una vez interpretados, se convierten en elementos de página utilizables, como texto, botones, formularios, enlaces, imágenes y contenedores de layout, que pertenecen a “Components, Controls, & Layouts”. La página se organiza entonces en “Graphs & Frames”, mencionado antes como el Document Object Model. Desde ahí, el “Renderer” del navegador prepara la página para presentarla. El navegador aparece dentro de una “Window” proporcionada por el sistema operativo, que entonces sirve como “System” que entrega el resultado a la “Human Interface”.

## La necesidad de Connectors

Durante el desarrollo temprano de CatalystUI, creíamos que el Stack por sí solo podría bastar para describir una interfaz de usuario. Al principio, parecía razonable. El Stack ya proporciona una forma más clara y completa de identificar cada parte de una interfaz de usuario que muchos modelos existentes. Pero cuando empezamos a usarlo como base para desarrollo real, todavía faltaba algo. Podíamos describir _qué_ era cada pieza. Podíamos describir _dónde_ pertenecía. Pero seguía habiendo un hueco entre ellas: _cómo_ se movían los datos entre capas. El Stack nos daba el camino, pero todavía no explicaba el movimiento de una capa a la siguiente. Para completar el Modelo, necesitábamos definir esas transiciones. Aquí es cuando los “Connectors” pasan a ser no solo un concepto adicional, sino una necesidad.
