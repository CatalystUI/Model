# 5. Le Stack

## Vue d’ensemble de haut niveau

Après avoir classé _quel_ type de données est impliqué dans le flux, nous pouvons nous concentrer sur _l’endroit_ où ces données se trouvent. C’est là que l’analyse des solutions existantes peut vraiment devenir utile, surtout lorsqu’on examine leurs différences. Avant de disséquer chaque solution, nous pouvons identifier deux vérités fondamentales pour donner à notre analyse une base solide : premièrement, les _données_ doivent exister quelque part, qu’elles soient stockées en binaire, sur un disque, en mémoire ou sous toute autre forme de stockage de données ; deuxièmement, une _personne_ doit également exister quelque part, que ce soit à l’autre bout d’un écran, d’un casque, d’une manette ou de toute autre forme d’interface. Nous considérerons ces deux concepts comme un sandwich, avec « Data Storage » comme pain du dessus et « Human Interface » comme pain du dessous. Comme ces deux concepts sont évidents, une fois identifiés comme parties du flux d’information, nous les appellerons _implicites_, puisque la nature du flux _implique_ leur existence.

### Les couches du Stack

À partir de l’interface humaine, nous pouvons commencer à identifier la première couche et le premier grand motif du Stack : la présence d’un « système ». Un système est responsable de l’organisation de la manière dont l’information est finalement transmise à l’utilisateur. Dans la plupart des ordinateurs modernes, ce rôle est rempli par un « système d’exploitation » (« OS »), qui fait le lien entre le matériel et le logiciel d’un ordinateur. Quelle que soit sa forme, dans tout flux d’information, un système doit exister pour accomplir l’étape finale qui relie le travail interne de l’interface à ce que l’utilisateur expérimente.

Pour qu’un système soit utile, l’utilisateur a besoin d’un moyen d’interagir avec lui. Dans une « interface graphique utilisateur » (« GUI »), cela se fait généralement par une fenêtre. Cependant, le Modèle CatalystUI considère l’idée de « fenêtre graphique » comme trop étroite, puisque toutes les interfaces ne sont pas graphiques. À la place, la couche suivante du Stack, une « window », est définie comme Layer 2 et consiste en toute « vue » sur un système. Il peut s’agir d’une fenêtre d’application traditionnelle, d’une interface en ligne de commande, d’un terminal visuel, d’un dispositif de capture audio ou de tout autre contexte dans lequel l’utilisateur peut fournir une entrée au système ou recevoir une sortie de celui-ci.

Pour permettre à l’information de circuler dans une window, un « renderer » est nécessaire afin de transformer les données entre la forme interne utilisée par l’interface et la forme perceptible utilisée par l’utilisateur, en agissant comme Layer 3. Dans une GUI, cela apparaît souvent comme une bibliothèque telle qu’OpenGL ou Vulkan, convertissant des données visuelles en sortie pouvant être affichée dans une fenêtre. Toutefois, les renderers ne se limitent pas aux graphiques. Les renderers audio, tels qu’OpenAL, WASAPI, ASIO ou CoreAudio, peuvent produire du son, tandis que les renderers haptiques peuvent produire un retour tactile. Dans la plupart des cas, les interactions passent avec peu de modification, mais peuvent être réinterprétées ou redéfinies, par exemple lors du traitement de données de mouvement provenant d’un capteur infrarouge. Quel que soit le domaine des données, le renderer est responsable de convertir l’information entre les données préparées par l’interface et la forme propre au domaine utilisée pour la sortie.

Après le renderer vient un ensemble de couches qui organisent et suivent les données dans l’interface. Ces couches peuvent être difficiles à distinguer au début, mais elles deviennent plus claires lorsque nous considérons ce que chacune fournit, la première étant Layer 4 : « Graphs & Frames ». Dans le Modèle CatalystUI, un « graph » représente une structure organisée préparée pour le rendu, comme un objet dans un monde 3D, une arborescence de composants ou une sous-section d’une interface. Un « frame » représente le contexte plus large qui contient et coordonne les graphs disponibles, les préparant à être transmis au renderer. Un exemple familier se trouve sur le web : le « Document Object Model » (« DOM ») organise les éléments d’une page web comme un graph, tandis que le document lui-même fournit le frame plus large dans lequel ces éléments existent.

Comme cette forme d’information est optimisée pour le renderer plutôt que pour l’interprétation par l’utilisateur, nous devons introduire une couche qui sépare les données dans leur forme logique afin qu’elles puissent être reconnues, organisées ou utilisées dans une interaction. C’est là que se déroule la plupart du traitement des interactions, et le Modèle CatalystUI appelle donc Layer 5 : « Components, Controls, & Layouts ». Un « component » est toute partie logique de l’interface, comme une image, un libellé, une piste audio, un élément de style ou un autre objet que le système peut présenter ou organiser. Un « control » traite les interactions, comme un bouton, un interrupteur, un curseur ou une entrée variable. Un « layout » arrange d’autres components ou controls et les place dans un ordre significatif. Dans une interface graphique, ces distinctions peuvent apparaître comme des éléments visuels, des controls cliquables et des lignes ou colonnes. Mais le même motif s’applique aussi en dehors du graphique : une interface audio peut utiliser des components pour représenter des pistes ou des effets sonores, des controls pour les lire ou les ajuster, et des layouts pour les organiser en groupes. Cette couche est essentielle parce qu’elle représente la structure utilisable de l’interface : les parties qui existent, les parties qui peuvent répondre et la façon dont ces parties sont arrangées avant d’être organisées en graphs et préparées pour le rendu.

Les parties logiques de l’interface sont soutenues par « Structure & Semantics », Layer 6. Cette couche décrit comment les données doivent être comprises avant de devenir des components, controls ou layouts. « Semantics » définit les règles de lecture des données : ce qu’elles signifient, l’ordre qu’elles suivent et comment chaque partie doit être comprise. « Structure » est la forme organisée de ces données après l’application de ces règles. Autrement dit, cette couche prend des données qui peuvent n’exister que sous forme de texte, d’octets, de champs ou d’enregistrements, et leur donne une forme signifiante que le reste de l’interface peut utiliser. Sur le web, par exemple, le HTML chargé commence comme Digital Data, et ses règles définissent comment il doit être interprété. La structure du document analysé est le résultat organisé de l’application de ces règles au HTML original.

Enfin, nous atteignons le sommet du Stack, Layer 7 : « Digital Data » lui-même. Cette couche représente les données avant que le reste du Modèle ne les ait lues, organisées ou présentées. Il peut s’agir d’un fichier, d’un document, d’un flux, d’une réponse web ou d’une autre représentation similaire. À ce stade, elles n’ont pas encore été façonnées en structure ni assignées à un domaine sensoriel. Un document texte, par exemple, n’est pas encore visuel ou auditif. Il est simplement du texte stocké. Le Stack peut plus tard choisir de l’afficher à l’écran ou de le lire à voix haute par un haut-parleur, l’assignant ainsi à un domaine. Digital Data est donc le point de retournement supérieur du flux : une interaction peut monter et changer ce qui est stocké, et ce qui est stocké peut plus tard redescendre le long du Stack pour devenir une partie de l’expérience utilisateur.

### Le rôle du Stack dans le Modèle

Maintenant que chaque élément du Stack a été identifié, nous pouvons décrire le Modèle dans son ensemble. De haut en bas, le Stack se compose de « Data Storage » (implicite), « Digital Data », « Structure & Semantics », « Components, Controls, & Layouts », « Graphs & Frames », « Renderers », « Windows », « Systems » et « Human Interface » (implicite). Les sept couches explicites sont numérotées de bas en haut, « Systems » étant Layer One et « Digital Data » Layer Seven. Les couches implicites se situent en dehors de cette numérotation et servent de points d’extrémité du flux. Ensemble, elles nous donnent une manière complète de suivre le flux d’information à travers une interface. Elles nous permettent de demander où se trouve quelque chose dans le processus, quel rôle cela remplit et comment cela contribue à l’achèvement de l’interaction. Parce que le Stack décrit le motif plutôt qu’une implémentation exacte, nous n’avons pas besoin de connaître chaque détail interne d’un système pour commencer à le comprendre. Cela fait partie de ce qui rend le Modèle puissant, surtout à une époque où les grands modèles de langage, les systèmes d’apprentissage automatique et d’autres formes d’architecture pilotée par « l’IA » peuvent rendre les rouages internes d’une interface plus difficiles à voir.

### Démonstration du Stack

#### Un capteur de porte

Pour le démontrer, nous pouvons revenir à l’exemple du capteur de porte. Plus tôt, nous avons résumé l’échange ainsi : l’utilisateur voit un chemin à suivre, entre dans la zone de détection, le système ouvre la porte, et le cycle se termine une fois que l’utilisateur est passé et que la porte se referme. Le Stack nous permet de décrire ce même processus plus en détail sans connaître la conception matérielle exacte.

L’action commence à la « Human Interface », où l’utilisateur s’approche de la porte, et atteint le « System », comme un contrôleur, un câblage, une source d’alimentation et un ensemble moteur. La « Window » détecte la présence de l’utilisateur via un capteur de mouvement ou un détecteur de chaleur, tandis que le « Renderer » convertit ce signal physique en événement utilisable. « Graphs & Frames » place l’événement dans le contexte plus large de la porte, y compris la zone de détection et l’état actuel de la porte. « Components, Controls, & Layouts » prend la décision elle-même, déterminant si la porte doit s’ouvrir, rester ouverte ou se fermer. Pour prendre cette décision, le control peut s’appuyer sur « Structure & Semantics », comme un format de configuration qui indique où se trouvent des réglages tels que la sensibilité ou le délai. Ces réglages et changements d’état sont alors représentés comme « Digital Data » et, s’ils doivent être conservés, placés dans « Data Storage ».

Une fois la décision prise, le flux redescend le long du Stack : l’état mis à jour de la porte est interprété, transformé en action de control, replacé dans le contexte de la porte, converti par le « Renderer » en quelque chose que le matériel peut exécuter, transmis par la « Window » du mécanisme de porte, réalisé par le « System » et enfin reçu par la « Human Interface ». Finalement, l’utilisateur voit la porte s’ouvrir et passe à travers.

#### Le Web

Pour un second exemple, nous pouvons regarder le web. Le web est l’une des tentatives existantes les plus proches d’un large modèle d’interface utilisateur, notamment grâce au W3C et à ses interfaces standardisées. Cependant, comme il est principalement conçu autour de la communication entre ordinateurs, il ne capture pas à lui seul chaque partie du Stack. Sur une page web typique, « Data Storage » peut être représenté par le serveur, la base de données, le système de fichiers ou l’API qui héberge la page. Lorsque le navigateur récupère du HTML, du CSS, du JavaScript, des images et des ressources similaires, ceux-ci deviennent « Digital Data ». Les règles de lecture, telles que la sémantique HTML, le style CSS et le comportement JavaScript, appartiennent à « Structure & Semantics ». Une fois interprétées, elles deviennent des éléments de page utilisables, comme du texte, des boutons, des formulaires, des liens, des images et des conteneurs de layout, qui appartiennent à « Components, Controls, & Layouts ». La page est ensuite organisée en « Graphs & Frames », déjà mentionné comme le Document Object Model. De là, le « Renderer » du navigateur prépare la page pour sa présentation. Le navigateur apparaît dans une « Window » fournie par le système d’exploitation, qui sert alors de « System » livrant le résultat à la « Human Interface ».

## Le besoin de Connectors

Au début du développement de CatalystUI, nous pensions que le Stack seul pourrait suffire à décrire une interface utilisateur. Au départ, cela semblait raisonnable. Le Stack fournit déjà une manière plus claire et plus complète d’identifier chaque partie d’une interface utilisateur que beaucoup de modèles existants. Mais lorsque nous avons commencé à l’utiliser comme fondation pour un développement réel, quelque chose manquait encore. Nous pouvions décrire _ce que_ chaque pièce était. Nous pouvions décrire _où_ elle appartenait. Mais il restait encore un écart entre elles : _comment_ les données se déplaçaient-elles entre les couches ? Le Stack nous donnait le chemin, mais il n’expliquait pas encore le mouvement d’une couche à la suivante. Pour compléter le Modèle, nous devions définir ces transitions. C’est là que les « Connectors » deviennent non seulement un concept supplémentaire, mais une nécessité.
