# 6. Connectors

## Vue d’ensemble de haut niveau

Les connectors sont uniques parce qu’ils font plus que décrire _comment_ l’information se déplace entre les couches ; ils nous permettent également d’_abstraire_ bon nombre des limites imposées par les périphériques matériels. Nous savons que c’est une affirmation audacieuse. Cependant, lorsqu’une interface utilisateur est correctement conçue autour du Stack CatalystUI, les connectors peuvent être construits de manière à pouvoir être remplacés par différentes implémentations selon les besoins. En ce sens, les connectors agissent comme un _support de traduction pour l’information_. Contrairement aux couches du Stack, qui sont généralement verrouillées sur un domaine spécifique une fois assignées, les connectors peuvent transformer l’information d’un domaine vers un autre. Par exemple, un connector pourrait prendre du texte stocké et le préparer pour un écran, un haut-parleur ou même un retour tactile via un afficheur braille !

De la même façon que nous avons identifié chaque couche du Stack, nous pouvons repérer nos connectors en déterminant où une couche doit communiquer avec une autre. C’est une distinction importante : contrairement à « Data Storage » et à la « Human Interface », les connectors n’ont pas de points d’extrémité implicites. Ils sont plutôt le mécanisme qui permet à deux couches voisines de travailler ensemble. Pour cette raison, chaque connector est défini par les deux couches explicites entre lesquelles il se trouve et par le type de communication qu’il doit prendre en charge.

### Les Connectors du Stack

Au sommet du Stack, la première connexion requise se situe entre Layer 7, « Digital Data », et Layer 6, « Structure & Semantics ». Digital Data peut contenir le matériau d’origine, comme un fichier, un document, une réponse ou un résultat de base de données, mais la couche suivante doit savoir comment ce matériau doit être lu. Cela signifie que le connector entre elles doit faire entrer le contenu stocké dans le Modèle tout en préservant son format et sa signification. Un fichier de paramètres JSON, par exemple, peut commencer comme du texte stocké, mais il doit être lu comme du JSON avant que l’interface puisse savoir quels paramètres sont disponibles. Comme ce connector convertit du contenu numérique en format structuré, nous pouvons le classer comme connector « Data ».

Une fois ce contenu lu dans une structure signifiante, la connexion suivante apparaît entre Layer 6, « Structure & Semantics », et Layer 5, « Components, Controls, & Layouts ». Layer 6 peut expliquer ce que le contenu signifie, mais Layer 5 doit encore savoir quelles parties utilisables doivent en être créées. Autrement dit, ce connector doit transformer une « instruction » en « réalité ». Si une description de page dit qu’il doit y avoir un bouton, l’étape suivante n’est pas simplement de _savoir_ que le bouton existe ; l’interface doit _créer_ le bouton comme un control fonctionnel. Comme ce connector _analyse_ des structures pour en faire des parties d’interface utilisables, il semble approprié de l’identifier comme connector « Parser ».

Une fois ces parties utilisables en place, la connexion suivante se trouve entre Layer 5, « Components, Controls, & Layouts », et Layer 4, « Graphs & Frames ». Layer 5 peut décrire ce que l’interface contient et comment ces parties doivent se comporter, mais Layer 4 a besoin que cette information soit organisée dans un contexte plus large. Cela signifie que le connector entre elles doit prendre les parties de l’interface et les placer dans des relations pouvant être suivies, coordonnées et préparées pour l’étape suivante. Un bouton, par exemple, peut déjà exister comme control, mais il a encore besoin d’une position, d’une taille, d’un état et d’une relation avec le frame environnant avant que le reste de l’interface puisse le traiter comme partie d’une scène complète. Comme ce connector _adapte_ des parties d’interface utilisables en structures de graph et de frame, nous pouvons l’identifier comme connector « Adapter ».

À partir de là, le frame organisé doit communiquer avec Layer 3, « Renderers », par une connexion à Layer 4, « Graphs & Frames ». Layer 4 peut décrire ce qui existe dans l’interface et comment chaque partie se rapporte à l’ensemble, mais Layer 3 a besoin d’instructions qu’il peut produire. Cela signifie que le connector entre elles doit traduire la scène organisée en travail adapté à un système de rendu spécifique. Dans une interface visuelle, un bouton dans un frame peut devoir être converti en rectangles, textures, glyphes ou commandes de dessin avant de pouvoir apparaître à l’écran. Comme ce connector _fait le pont_ entre l’interface organisée et le renderer qui la produit, nous pouvons l’identifier comme connector « Bridge ».

Après que le renderer a préparé son travail, la connexion suivante apparaît entre Layer 3, « Renderers », et Layer 2, « Windows ». Layer 3 peut savoir dessiner, jouer ou produire quelque chose d’une autre manière, mais il lui faut encore une cible vers laquelle ce travail peut être livré. Layer 2 fournit la vue par laquelle l’utilisateur le reçoit ; le connector entre elles doit donc exposer un endroit utilisable où le renderer peut envoyer son résultat. OpenGL, par exemple, peut dessiner une scène, mais il lui faut un endroit où la placer avant que l’image puisse apparaître à l’utilisateur. Comme ce connector fournit la _surface_ où le travail rendu rencontre la window, nous pouvons l’identifier comme connector « Surface ».

Enfin, le bas du Stack exige une communication entre Layer 2, « Windows », et Layer 1, « Systems ». À ce point, le connector doit fonctionner dans la forme que Layer 1 comprend naturellement, qu’il s’agisse d’un handle de système d’exploitation, d’une API de plateforme, d’un signal de périphérique ou d’un mécanisme physique. Dans une application de bureau, cela peut être le handle natif utilisé pour créer et gérer Layer 2. Dans une porte automatique, cela peut être la connexion intégrée au capteur et au moteur qui permet à la porte de répondre. Comme ce connector communique avec le système dans sa forme _native_, nous l’identifierons comme connector « Native ».

### Le rôle des Connectors dans le Modèle

Maintenant que chaque connector a été identifié, nous pouvons décrire plus complètement le mouvement du Modèle. De haut en bas, les connectors sont « Data », « Parser », « Adapter », « Bridge », « Surface » et « Native ». Chacun se trouve entre deux couches explicites du Stack et explique comment ces couches communiquent. Le connector Data fait entrer le contenu stocké dans une structure que le Modèle peut comprendre. Le connector Parser transforme cette structure en parties d’interface utilisables. Le connector Adapter place ces parties dans des graphs et des frames. Le connector Bridge prépare ces structures organisées pour le renderer. Le connector Surface donne au renderer un endroit où livrer son résultat. Enfin, le connector Native permet à la window de communiquer avec le system selon les propres termes du system.

### Connectors et l’échange vivant

Ensemble, ces connectors complètent le chemin décrit par le Stack. Les couches nous disent où se trouve l’information dans le flux, tandis que les connectors nous disent comment elle passe d’une étape à la suivante. C’est ce qui permet au Modèle CatalystUI de décrire plus qu’un arrangement statique de parties. Il décrit un échange vivant : le contenu stocké devient structure, la structure devient interface, l’interface devient sortie, la sortie atteint l’utilisateur, et la réponse de l’utilisateur peut revenir par le même motif. Parce que les connectors peuvent être remplacés ou retravaillés sans redéfinir les couches elles-mêmes, ils donnent aussi au Modèle l’une de ses forces les plus importantes : la capacité de s’adapter à différents dispositifs, domaines et systèmes tout en conservant le même flux d’information sous-jacent.
