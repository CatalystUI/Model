# 6.2 Connectors :: Parser

## بحث عمیق

### از تفسیر به استفاده

اتصال‌دهنده **Parser** میان **Layer 6: Structure & Semantics** و **Layer 5: Components, Controls, & Layouts** قرار دارد. وظیفه آن تبدیل داده تفسیرشده و معمولاً immutable به عناصر mutable و قابل استفاده در رابط است.

Layer 6 می‌گوید داده چیست و چگونه باید فهمیده شود. Layer 5 می‌خواهد با داده کار کند: آن را نمایش دهد، تغییر دهد، به interaction پاسخ دهد، آن را در layout قرار دهد یا به component و control تبدیل کند. Parser connector این انتقال را انجام می‌دهد.

### چرا Parser لازم است

یک structure ممکن است برای خواندن داده عالی باشد، اما لزوماً برای تعامل مناسب نیست. ساختار یک فایل پیکربندی می‌تواند keys و values را نشان دهد، اما رابط ممکن است به text field، toggle، dropdown یا validation message نیاز داشته باشد. ساختار MP3 می‌تواند metadata و frames را نشان دهد، اما رابط ممکن است به audio component با `Play()` و `Pause()` نیاز داشته باشد.

Parser این فاصله را پر می‌کند. داده‌ای که فقط قابل فهم بود، حالا قابل استفاده می‌شود.

### حفظ قرارداد Semantics

Parser باید به semantics احترام بگذارد. اگر semantics می‌گوید فیلدی اختیاری است، parser نباید آن را بی‌دلیل اجباری کند. اگر ترتیب، نوع یا محدوده‌ای تعریف شده، parser باید آن قرارداد را در componentهای خروجی منعکس کند. در غیر این صورت Layer 5 از داده‌ای استفاده می‌کند که دیگر با حقیقت Layer 6 هم‌خوان نیست.

### Mutable کردن بدون از دست دادن معنا

یکی از نقش‌های مهم Parser این است که نمایش immutable لایه 6 را به اشیای mutable لایه 5 تبدیل کند بدون اینکه معنای اصلی گم شود. Componentها می‌توانند تغییر کنند، اما باید بدانند تغییرشان به چه structure یا semantic مربوط است. این ارتباط اجازه می‌دهد پس از interaction، تغییرات دوباره به لایه‌های بالاتر داده برگردند.

### Parser در دامنه‌های مختلف

Parser فقط مخصوص متن یا فایل نیست. می‌تواند فایل صوتی را به audio component، سند را به document components، داده بصری را به image components یا پیکربندی را به controls تبدیل کند. در هر مورد، وظیفه اصلی همان است: تفسیر را به استفاده تبدیل کند.
