# 5.7 The Stack :: Windows

## Подробное обсуждение

### Слой ограниченной доставки

**Windows** — это слой, где отрендеренный output получает ограниченный контекст доставки. Layer 3 преобразует подготовленное состояние интерфейса в output-ready форму, но этому output всё ещё нужно определённое место, channel или view, через которые system сможет его доставить. Layer 2 предоставляет эту границу.

Window следует понимать как логический контекст доставки, а не просто как визуальную рамку на экране. В графической среде window обычно выглядит как видимая область, управляемая операционной системой. Однако в Модели понятие шире: window — это system-facing контекст, через который output может быть предоставлен, а interaction может быть получено. Он определяет, где отрендеренный результат принадлежит внутри окружающей системы.

### Взгляд внутрь системы

Window действует как взгляд внутрь system. Он не создаёт system и не заменяет renderer. Вместо этого он предоставляет ограниченный контекст, где output renderer может быть связан с доставкой на уровне system. Эта граница может включать позицию, размер, фокус, видимость, контекст устройства, output channel или другую форму области, определённой system.

Это важно, потому что отрендеренный output не существует для пользователя изолированно. Его нужно куда-то доставить. Renderer может произвести visual commands, audio samples, haptic instructions или другой domain-specific output, но эти результаты всё равно должны быть связаны с контекстом, распознаваемым system. Window предоставляет эту связь.

В визуальных интерфейсах это легко распознать, потому что window может соответствовать прямоугольной области на дисплее. В других domains ту же концептуальную роль может выполнять сессия командной строки, audio output context, device channel, virtual viewport или другой ограниченный system-facing interface. Определяющий признак — не визуальный вид. Определяющий признак в том, что window предоставляет границу доставки между отрендеренным output и system.

### Отношение к Renderers

Windows получают output от Renderers, но не выполняют rendering сами. Rendering — это преобразование подготовленного состояния интерфейса в output-ready форму. Windowing — это действие, которое даёт этому output ограниченный системный контекст, через который он может быть доставлен.

Это различие не даёт Layer 2 поглотить ответственности Layer 3. Renderer должен решать, как организованное состояние интерфейса становится output-ready. Window должен предоставлять system-facing место или channel, куда этот output можно отправить. Renderer преобразует; window содержит, получает и пересылает.

Это также позволяет разным renderers нацеливаться на разные типы window. Visual renderer может нацеливаться на graphical window, а auditory renderer — на audio output context. Конкретная реализация может различаться по system и domain, но слоистая ответственность остаётся согласованной.

### Отношение к System

Windows зависят от **Layer 1: Systems**, потому что обычно создаются, управляются, ограничиваются или распознаются окружающей платформой. System может определять, как создаются windows, как они получают input, как раскрывают output channels, к каким ресурсам имеют доступ и как взаимодействуют с hardware или lower-level services.

Это не делает window идентичным system. System — это более широкая operating environment, предоставляющая hardware access, device services, scheduling, permissions, drivers и platform behavior. Window — это ограниченный логический контекст внутри этой среды. Это interface-facing контекст, который позволяет отрендеренному output и interaction проходить между Stack и system.

Отделяя Windows от System, Модель избегает трактовки каждой детали платформы как части границы интерфейса. Window представляет конкретный system-facing контекст, используемый интерфейсом. System представляет более широкую среду, которая делает этот контекст возможным.

### Доставка output

В потоке сверху вниз window получает output-ready representation от renderer и передаёт его к system. Это этап, где отрендеренный output уже не просто подготовлен интерфейсом; он назначен контексту доставки, который system может использовать.

Window может управлять границами, фокусом, buffering, видимостью, состоянием channel или другими условиями доставки в зависимости от domain и реализации. Эти детали влияют на то, как output движется в system, но не меняют главную роль слоя. Window предоставляет границу, через которую отрендеренный output может стать system output.

После того как output проходит через window, system может перенести его к соответствующему устройству, сервису или физическому процессу, который позволяет пользователю его воспринять. Поэтому window близок к воспринимаемости, но не является самим восприятием. Он остаётся частью потока на стороне компьютера.

### Вход взаимодействия

В потоке снизу вверх window — первый явный слой Stack, где interaction, предоставленное system, становится доступным моделируемому интерфейсу. System может обнаружить нажатие клавиши, движение указателя, touch event, сигнал устройства, аудиокоманду или другую форму input. Window получает это interaction внутри своего ограниченного контекста и пересылает его вверх для дальнейшей маршрутизации и обработки.

Это делает window центральным для interaction, потому что он предоставляет контекст действия. Interaction — это не только то, что что-то произошло, но и то, что оно произошло внутри конкретной system-facing границы. Фокус, позиция, время, источник устройства, channel или активный контекст могут определять, как остальная часть Stack должна понять и маршрутизировать interaction.

Window обычно не решает окончательное значение interaction. Эта ответственность находится выше в Stack, особенно когда interaction достигает соответствующего control. Роль window — получить interaction от system, связать его с правильной границей и передать вверх в форме, которую остальная часть Stack может продолжить обрабатывать.

### Независимость от домена

Windows независимы от domain так же, как и остальной Stack. Слово «window» часто связано с графикой, но в CatalystUI оно означает любой ограниченный system-facing контекст для output и interaction. Domain определяет, какой вид output и input несёт window; положение в Stack определяет, какую роль window выполняет.

Это позволяет одному и тому же слою описывать graphical windows, text sessions, audio channels, tactile output contexts или другие формы interface delivery без изменения Модели. У каждой реализации могут быть разные system requirements, но каждая выполняет одну и ту же концептуальную ответственность: предоставляет границу, через которую проходят отрендеренный output и system interaction.

### Почему слой важен

Windows не даёт Stack обращаться с отрендеренным output так, будто он автоматически достигает пользователя. Renderer может преобразовать состояние интерфейса в output-ready форму, но этому output всё ещё нужен system-facing контекст. Layer 2 предоставляет этот контекст.

Отделяя Windows и от Renderers, и от System, Модель сохраняет чистый путь доставки. Renderers преобразуют подготовленное состояние интерфейса в output-ready representation. Windows предоставляет ограниченный контекст, через который это представление входит в system. System затем выполняет нижнеуровневую работу, необходимую для доставки output и получения input. Это различие позволяет CatalystUI описывать interface delivery на разных платформах и в разных доменах, не сводя windows к визуальным прямоугольникам и не заставляя renderers управлять platform-level behavior.
