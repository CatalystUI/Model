# 4.3 Domains :: Auditory

## Ausführliche Besprechung

Nach der visuellen Domain beschreibt die **auditive** Domain Daten, die für das Hören geformt wurden. Auditive Daten sind Informationen, die durch Klang wahrgenommen werden sollen: gesprochene Wörter, Musik, Hinweise, Töne oder jede andere Ausgabe, die der Benutzer durch Zuhören versteht. Während visuelle Daten Bedeutung in eine durch Sehen lesbare Form bringen, ordnen auditive Daten Bedeutung in zeitbasiertem Klang an.

Dadurch unterscheidet sich die auditive Domain auf wichtige Weise von der visuellen Domain. Visuelle Information kann oft auf einmal erfasst werden, aber auditive Information entfaltet sich normalerweise über Zeit. Ein Benutzer kann auf einen Bildschirm blicken und sofort mehrere Beziehungen erkennen, aber ein Klang muss in Abfolge gehört werden. Deshalb hängen auditive Daten stark von Timing, Reihenfolge, Dauer und Rhythmus ab. Die Bedeutung liegt nicht nur darin, was gehört wird, sondern auch darin, wann es gehört wird und wie es sich verändert.

Eine gespeicherte Audiodatei ist nicht schon deshalb auditiv, weil sie Klangdaten enthält. Solange sie gespeichert, codiert oder abstrakt dargestellt bleibt, ist sie weiterhin symbolisch. Sie wird auditiv, wenn das System sie als wahrnehmbaren Klang erzeugt. Dasselbe gilt für geschriebenen Text, der von einem Screenreader vorgelesen wird, für eine Benachrichtigung, die in einen Signalton übersetzt wird, oder für ein Spielereignis, das durch Musik ausgedrückt wird. In jedem Fall hat das System Information genommen und sie dem Hören zugeordnet.

### Auditive Daten verstehen

Eine hilfreiche Möglichkeit, auditive Daten zu verstehen, besteht darin, **Inhalt**, **Timing** und **Ton** zu betrachten. Dies sind keine formalen Kategorien des Modells, aber sie helfen zu erklären, wie Klang Bedeutung anders trägt als das Sehen.

**Inhalt** beschreibt, was der Klang kommuniziert. Bei gesprochener Ausgabe können dies die vorgelesenen Wörter sein. In Musik können es Melodie, Harmonie oder Fortschreitung sein. Bei einer Benachrichtigung kann es das erkennbare Muster sein, das dem Benutzer mitteilt, dass etwas passiert ist. Auditiver Inhalt ist die Substanz dessen, was der Benutzer hören und verstehen soll.

**Timing** beschreibt, wann der Klang geschieht und wie lange er dauert. Ein Warnton, der zu spät abgespielt wird, kann seine Nützlichkeit verlieren. Eine gesprochene Nachricht, die zu schnell abläuft, kann schwer zu verfolgen sein. Musik, die sofort auf eine Benutzerhandlung reagiert, kann verbunden wirken, während verzögerter Klang das System unverbunden wirken lassen kann. Timing ist wichtig, weil auditive Daten in Bewegung erlebt werden.

**Ton** beschreibt die Qualität oder den Charakter des Klangs. Ein sanfter Klang, ein scharfes Piepen und eine ruhige gesprochene Stimme können sehr unterschiedliche Bedeutungen kommunizieren, selbst wenn sie alle kurze auditive Signale sind. Ton hilft dem Benutzer, Dringlichkeit, Stimmung, Bestätigung, Warnung oder Abschluss zu verstehen. Er gibt Klang seinen emotionalen und praktischen Charakter.

### Auditive Bedeutung

Auditive Ausgabe drückt Bedeutung durch Klang aus, aber der Klang selbst sollte nicht mit der gesamten Bedeutung verwechselt werden. Ein Warnton kann ein Problem kommunizieren, aber der Ton ist nicht das Problem. Eine gesprochene Beschriftung kann Text kommunizieren, aber die Stimme ist nicht die zugrunde liegende Struktur. Ein musikalisches Signal kann Erfolg, Gefahr oder Übergang kommunizieren, aber die Bedeutung entsteht daraus, wie das System dieses Signal innerhalb der Erfahrung verwendet.

Diese Unterscheidung ist wichtig, weil Klang stark sein kann, ohne präzise zu sein. Ein kurzer Ton kann die Aufmerksamkeit des Benutzers gewinnen, aber er erklärt möglicherweise nicht, was passiert ist. Eine gesprochene Nachricht kann klar erklären, aber sie dauert möglicherweise länger als ein visueller Hinweis. Musik kann das Gefühl einer Erfahrung formen, aber sie kommuniziert möglicherweise keine genauen Anweisungen. Auditives Design ist am stärksten, wenn der Klang zu der Art von Bedeutung passt, die das System ausdrücken muss.

Auditive Daten wirken außerdem anders auf den Benutzer als visuelle Daten, weil Klang den Benutzer erreichen kann, ohne dass er direkt auf das System schauen muss. Ein Timer kann aus einem anderen Raum klingeln. Eine Navigations-App kann sprechen, während die Augen des Benutzers auf der Straße bleiben. Ein Screenreader kann einem Benutzer ermöglichen, Software zu bedienen, ohne vom Sehen abhängig zu sein. Das macht die auditive Domain besonders wertvoll, wenn Aufmerksamkeit geteilt ist, Sehen nicht verfügbar ist oder Klang der klarste Kommunikationsweg ist.

### Auditive Daten und Barrierefreiheit

Die auditive Domain ist zentral für Barrierefreiheit, weil sie Informationen tragen kann, die sonst visuell eingeschlossen wären. Text kann gesprochen werden. Der Zustand einer Schnittstelle kann angesagt werden. Navigation kann durch Klang geführt werden. Für manche Benutzer ist auditive Ausgabe keine Verbesserung, sondern der primäre Weg, durch den das System nutzbar wird.

Gleichzeitig kann auditive Information auch Barrierefreiheitsprobleme schaffen, wenn sie die einzige Weise ist, in der Bedeutung kommuniziert wird. Eine Warnung, die nur als Klang existiert, kann von einem gehörlosen oder schwerhörigen Benutzer verpasst werden. Eine gesprochene Anweisung kann in einer lauten Umgebung schwer zu verfolgen sein. Ein Klangeffekt kann eine Handlung bestätigen, aber wenn es keine andere Darstellung dieser Bestätigung gibt, wird die Bedeutung allein vom Hören abhängig.

Hier helfen Domains sichtbar zu machen, was das System tatsächlich tut. Wenn wichtige Bedeutung nur durch Klang getragen wird, kann der Entwickler fragen, ob sie auch symbolisch, visuell, taktil oder durch eine andere Form verfügbar sein sollte. Ziel ist nicht, auditives Design zu schwächen, sondern Bedeutung über die Arten hinweg zu bewahren, wie Benutzer das System tatsächlich wahrnehmen.

### Auditive Daten in umfassenderen Erfahrungen

Auditive Daten arbeiten oft neben anderen Domains. In einem Videoplayer kann Klang Sprache oder Musik tragen, während Bilder Bewegung tragen. In einem Spiel kann Audio Entfernung, Gefahr, Atmosphäre oder Feedback kommunizieren. In einem Betriebssystem kann Klang Benachrichtigungen, Fehler und Bestätigungen unterstützen. In jedem Fall identifiziert die auditive Domain den Teil der Erfahrung, der für das Hören geformt wurde.

Wenn Klang mit anderen Wahrnehmungsformen integriert wird, kann er Teil eines größeren multisensorischen Austauschs werden. Ein Klang zusammen mit einer visuellen Animation kann eine Handlung abgeschlossen wirken lassen. Eine gesprochene Richtung zusammen mit einer Karte kann den Benutzer klarer führen als jede Form allein. Eine Vibration zusammen mit einem Signalton kann dafür sorgen, dass eine Benachrichtigung schwerer zu verpassen ist. Der auditive Teil hat weiterhin seine eigene Rolle, aber die vollständige Erfahrung kann davon abhängen, wie die Domains zusammenarbeiten.

Kurz gesagt beschreibt die auditive Domain Informationen, die in hörbare Ausgabe geformt wurden. Sie hilft zu erklären, wie Systeme Klang nutzen, um Inhalt, Timing, Ton und Feedback zu kommunizieren. Wenn auditive Daten gut behandelt werden, kann der Benutzer hören, was das System präsentiert, erkennen, was sich verändert hat, und reagieren, ohne dass jeder Teil der Erfahrung sichtbar sein muss.
