# 5. The Stack

## High-Level Overview

flow में _किस_ type का data शामिल है, इसे classify करने के बाद, हम इस पर focus कर सकते हैं कि data _कहाँ_ located है। existing solutions का analysis यहीं बहुत useful हो सकता है, especially जब उनकी differences examine की जाती हैं। हर solution को dissect करने से पहले, हम दो fundamental truths पहचान सकते हैं ताकि analysis को ठोस आधार मिले: पहला, _data_ को कहीं न कहीं exist करना ही होगा, चाहे वह binary के रूप में stored हो, disk पर हो, memory में हो, या data storage के किसी और form में; और दूसरा, _person_ को भी कहीं न कहीं exist करना होगा, चाहे वह screen, headphones, controller, या interface के किसी और form के दूसरे side पर हो। हम इन दो concepts को sandwich की तरह देखेंगे, जिसमें “Data Storage” top bun है और “Human Interface” bottom bun। क्योंकि ये दोनों concepts, एक बार information flow के parts के रूप में पहचाने जाने के बाद, obvious हैं, हम इन्हें _implied_ कहेंगे, क्योंकि flow की nature इनके existence को _imply_ करती है।

### Stack की Layers

human interface से शुरू करते हुए, हम Stack में पहली layer और major pattern identify कर सकते हैं: “system” की presence। system इस बात को organize करने के लिए responsible है कि information अंततः user तक कैसे deliver होती है। अधिकांश modern computers में, यह role “operating system” (“OS”) निभाता है, जो computer hardware और software के बीच gap bridge करता है। उसका form चाहे जो भी हो, किसी भी information flow में system का exist करना आवश्यक है ताकि वह अंतिम step complete करे जो interface के internal work को user के experience से connect करता है।

system को useful बनाने के लिए, user को उससे interact करने का कोई तरीका चाहिए। “graphical user interface” (“GUI”) में यह सामान्यतः window के माध्यम से होता है। हालांकि, CatalystUI Model “graphical window” के idea को बहुत narrow मानता है, क्योंकि हर interface graphical नहीं होता। इसके बजाय, Stack की next layer, “window,” Layer 2 के रूप में define होती है और system में किसी भी “view” से बनी होती है। यह traditional application window, command-line interface, visual terminal, audio-capture device, या कोई भी context हो सकता है जिसमें user system को input दे सके या उससे output receive कर सके।

information को window में flow कराने के लिए “renderer” की आवश्यकता होती है, जो interface द्वारा उपयोग किए गए internal form और user द्वारा उपयोग किए गए perceivable form के बीच data transform करता है, और Layer 3 की तरह काम करता है। GUI में यह अक्सर OpenGL या Vulkan जैसी library के रूप में दिखाई देता है, जो visual data को ऐसे output में बदलती है जिसे window के माध्यम से display किया जा सके। लेकिन renderers graphics तक सीमित नहीं हैं। OpenAL, WASAPI, ASIO, या CoreAudio जैसे audio renderers sound produce कर सकते हैं, जबकि haptic renderers tactile feedback produce कर सकते हैं। ज्यादातर cases में interactions थोड़े modification के साथ pass through होते हैं, लेकिन कभी-कभी reinterpret या redefine हो सकते हैं, जैसे infrared sensor से motion data process करना। data का domain चाहे जो भी हो, renderer interface के prepared data और output के लिए उपयोग होने वाले domain-specific form के बीच information convert करने के लिए responsible है।

renderer के बाद layers का एक set आता है जो interface के भीतर data को organize और track करता है। ये layers पहले distinguish करना कठिन हो सकती हैं, लेकिन जब हम देखते हैं कि हर layer क्या provide करती है तो बात साफ़ होती है; पहली है Layer 4: “Graphs & Frames”. CatalystUI Model में “graph” rendering के लिए तैयार organized structure को represent करता है, जैसे 3D world में object, component tree, या interface का subsection। “frame” उस larger context को represent करता है जो available graphs को contain और coordinate करता है, उन्हें renderer को pass करने के लिए तैयार करता है। web पर familiar example मिलता है: “Document Object Model” (“DOM”) webpage elements को graph की तरह organize करता है, जबकि document itself वह larger frame देता है जिसमें वे elements exist करते हैं।

क्योंकि information का यह form user interpretation के बजाय renderer के लिए optimized होता है, हमें एक layer introduce करनी होती है जो data को उसकी logical form में separate करे ताकि उसे recognize, organize, या interact किया जा सके। अधिकांश interaction processing यहीं होती है, इसलिए CatalystUI Model Layer 5 को “Components, Controls, & Layouts” कहता है। “component” interface का कोई भी logical part है, जैसे image, label, audio track, style element, या कोई other object जिसे system present या organize कर सकता है। “control” interactions process करता है, जैसे button, toggle switch, slider, या variable input। “layout” other components या controls को arrange करता है और उन्हें meaningful order में रखता है। graphical interface में ये distinctions visual elements, clickable controls, और rows या columns के रूप में दिखाई दे सकती हैं। लेकिन वही pattern graphics के बाहर भी लागू होता है: audio interface tracks या sound effects represent करने के लिए components, उन्हें play या adjust करने के लिए controls, और उन्हें groups में organize करने के लिए layouts use कर सकता है। यह layer essential है क्योंकि यह interface की usable structure represent करती है: वे parts जो exist करते हैं, वे parts जो respond कर सकते हैं, और वह तरीका जिससे ये parts graphs में organize और rendering के लिए prepare होने से पहले arrange होते हैं।

interface के logical parts के पीछे “Structure & Semantics,” Layer 6 है। यह layer describe करती है कि data components, controls, या layouts बनने से पहले कैसे understood होना चाहिए। “Semantics” data पढ़ने के rules define करता है: उसका meaning क्या है, वह किस order का पालन करता है, और हर part को कैसे समझना चाहिए। “Structure” उन rules को apply करने के बाद data का organized form है। दूसरे शब्दों में, यह layer ऐसे data को, जो केवल text, bytes, fields, या records के रूप में exist कर सकता है, meaningful shape देती है जिसे interface का बाकी हिस्सा use कर सकता है। web पर, उदाहरण के लिए, loaded HTML Digital Data के रूप में शुरू होता है, और उसके rules define करते हैं कि उसे कैसे interpret किया जाना चाहिए। parsed document structure original HTML पर उन rules को apply करने का organized result है।

अंत में, हम Stack के top, Layer 7: “Digital Data” itself तक पहुँचते हैं। यह layer उस data को represent करती है जिसे Model के बाकी हिस्से ने अभी पढ़ा, organize, या present नहीं किया है। यह file, document, stream, web response, या कोई similar representation हो सकता है। इस point पर, उसे अभी structure में shape नहीं किया गया है या sensory domain assign नहीं किया गया है। text document, उदाहरण के लिए, अभी visual या auditory नहीं है। वह केवल stored text है। Stack बाद में उसे screen पर display करने या speaker से loud read करने का चुनाव कर सकता है, thereby उसे domain assign करता है। इसलिए Digital Data flow का upper turning point है: interaction ऊपर जा सकता है और stored चीज़ को बदल सकता है, और stored चीज़ बाद में Stack के नीचे आकर user experience का हिस्सा बन सकती है।

### Model में Stack की भूमिका

Stack के हर piece को identify कर लेने के बाद, हम Model को whole के रूप में describe कर सकते हैं। ऊपर से नीचे तक, Stack में “Data Storage” (implied), “Digital Data,” “Structure & Semantics,” “Components, Controls, & Layouts,” “Graphs & Frames,” “Renderers,” “Windows,” “Systems,” और “Human Interface” (implied) शामिल हैं। सात explicit layers bottom up numbered हैं, जहाँ “Systems” Layer One है और “Digital Data” Layer Seven। implied layers इस numbering के बाहर होती हैं और flow के endpoints के रूप में काम करती हैं। मिलकर वे हमें interface के through information flow trace करने का complete way देती हैं। वे हमें पूछने देती हैं कि process में कोई चीज़ कहाँ है, वह कौन-सी role serve कर रही है, और interaction complete होने में कैसे contribute करती है। क्योंकि Stack exact implementation के बजाय pattern describe करता है, हमें system की हर internal detail जानने की जरूरत नहीं होती ताकि हम उसे समझना शुरू कर सकें। यही Model को powerful बनाने वाली चीज़ों में से एक है, especially ऐसे समय में जब large-language models, machine-learning systems, और “AI”-driven architecture के other forms interface की inner workings को देखना कठिन बना सकते हैं।

### Stack का प्रदर्शन

#### Door Sensor

इसे demonstrate करने के लिए, हम door sensor example पर लौट सकते हैं। पहले हमने exchange को इस तरह summarize किया था: user आगे का path देखता है, detection area में enters करता है, system door खोलता है, और cycle तब समाप्त होती है जब user through pass करता है और door close होता है। Stack हमें exact hardware design जाने बिना उसी process को अधिक detail में describe करने देता है।

action “Human Interface” से शुरू होता है, जहाँ user doorway के पास आता है, और “System” तक पहुँचता है, जैसे controller, wiring, power source, और motor assembly। “Window” motion sensor या heat detector के माध्यम से user की presence detect करती है, जबकि “Renderer” उस physical signal को usable event में convert करता है। “Graphs & Frames” event को larger doorway context में place करता है, जिसमें detection area और current door state शामिल हैं। “Components, Controls, & Layouts” decision itself handle करता है, deciding whether door should open, remain open, or close। यह decision लेने के लिए control “Structure & Semantics” पर rely कर सकता है, जैसे configuration format जो sensitivity या delay timing जैसी settings कहाँ located हैं यह specify करता है। फिर ये settings और state changes “Digital Data” के रूप में represented होते हैं, और यदि retain करने की आवश्यकता हो तो “Data Storage” में रखे जाते हैं।

decision बन जाने के बाद, flow Stack के नीचे वापस move करता है: updated door state interpret होती है, control action में turn होती है, doorway context में वापस placed होती है, “Renderer” द्वारा hardware perform कर सके ऐसी चीज़ में convert होती है, door mechanism की “Window” से pass होती है, “System” द्वारा carried out होती है, और finally “Human Interface” द्वारा received होती है। अंत में, user door खुलते देखता है और through walk करता है।

#### Web

दूसरे example के लिए, हम web को देख सकते हैं। web एक broad user-interface model के सबसे करीब existing attempts में से एक है, especially W3C और उसकी standardized interfaces के through। हालांकि, क्योंकि यह mainly computers के बीच communication के around designed है, यह अपने आप Stack के हर part को capture नहीं करता। typical webpage में, “Data Storage” server, database, file system, या API द्वारा represented हो सकता है जो page host करता है। जब browser HTML, CSS, JavaScript, images, और similar resources fetch करता है, वे “Digital Data” बन जाते हैं। उन्हें read करने के rules, जैसे HTML semantics, CSS styling, और JavaScript behavior, “Structure & Semantics” से belong करते हैं। once interpreted, वे usable page elements बन जाते हैं, जैसे text, buttons, forms, links, images, और layout containers, जो “Components, Controls, & Layouts” से belong करते हैं। page फिर “Graphs & Frames” में organized होता है, जिसे पहले Document Object Model कहा गया था। वहाँ से browser का “Renderer” page को presentation के लिए prepare करता है। browser operating system द्वारा provided “Window” के अंदर दिखाई देता है, जो then “System” की तरह result को “Human Interface” तक deliver करता है।

## Connectors की आवश्यकता

CatalystUI के early development के दौरान, हमने माना कि Stack अकेले user interface describe करने के लिए पर्याप्त हो सकता है। पहले यह reasonable लगा। Stack कई existing models की तुलना में user interface के हर part को identify करने का clearer, more complete way देता है। लेकिन जब हमने उसे real development की foundation के रूप में use करना शुरू किया, कुछ अभी भी missing लगा। हम describe कर सकते थे कि हर piece _क्या_ था। हम describe कर सकते थे कि वह _कहाँ_ belong करता था। लेकिन उनके बीच gap अभी भी था: data layers के बीच _कैसे_ move करता था? Stack ने path दिया, लेकिन एक layer से next layer तक movement अभी explain नहीं किया। Model को complete करने के लिए, हमें उन transitions को define करना था। यहीं “Connectors” केवल additional concept नहीं, बल्कि necessity बन जाते हैं।
