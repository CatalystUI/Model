# 6. Connectors

## High-Level Overview

Connectors unique हैं क्योंकि वे केवल यह describe नहीं करते कि information layers के बीच _कैसे_ move करती है; वे हमें hardware devices द्वारा लगाए गए कई limitations को _abstract_ करने की अनुमति भी देते हैं। हम जानते हैं कि यह bold claim है; हालांकि, जब user interface CatalystUI Stack के around properly designed होता है, connectors ऐसे बनाए जा सकते हैं कि उन्हें आवश्यकता के अनुसार different implementations से swapped out किया जा सके। इस sense में, connectors information के लिए _translation medium_ की तरह काम करते हैं। Stack की layers के विपरीत, जो assignment के बाद generally किसी specific domain पर locked होती हैं, connectors information को एक domain से दूसरे domain में transform कर सकते हैं। उदाहरण के लिए, connector stored text लेकर उसे screen, speaker, या braille display के माध्यम से tactile feedback के लिए prepare कर सकता है!

जैसे हमने Stack में हर layer identify की, वैसे ही हम connectors को pinpoint कर सकते हैं यह determine करके कि कहाँ एक layer को दूसरी से communicate करने की आवश्यकता है। यह important distinction है: “Data Storage” और “Human Interface” के विपरीत, connectors के implied endpoints नहीं होते। इसके बजाय, वे वह mechanism हैं जो दो neighboring layers को साथ काम करने देते हैं। इसी वजह से हर connector उन दो explicit layers से define होता है जिनके बीच वह बैठता है, और उस communication के kind से जिसे उसे support करना होता है।

### Stack के Connectors

Stack के top पर, पहली required connection Layer 7, “Digital Data,” और Layer 6, “Structure & Semantics” के बीच बैठती है। Digital Data original material hold कर सकता है, जैसे file, document, response, या database result, लेकिन next layer को पता होना चाहिए कि उस material को कैसे read करना है। इसका मतलब है कि उनके बीच का connector stored content को Model में लाए, जबकि उसका format और meaning preserve करे। JSON settings file, उदाहरण के लिए, stored text के रूप में शुरू हो सकती है, लेकिन interface यह जान सके कि कौन-सी settings available हैं, उससे पहले उसे JSON के रूप में read होना चाहिए। क्योंकि यह connector digital content को structured format में convert करता है, हम इसे “Data” connector के रूप में classify कर सकते हैं।

एक बार content meaningful structure में read हो जाए, next connection Layer 6, “Structure & Semantics,” और Layer 5, “Components, Controls, & Layouts” के बीच दिखाई देती है। Layer 6 explain कर सकती है कि content का meaning क्या है, लेकिन Layer 5 को अभी भी जानना होता है कि उससे कौन-से usable parts create होने चाहिए। दूसरे शब्दों में, इस connector को “instruction” को “reality” में turn करना होता है। यदि page description कहता है कि button होना चाहिए, तो next step केवल यह _जानना_ नहीं है कि button exist करता है; interface को button को working control के रूप में _create_ करना होगा। क्योंकि यह connector structures को usable interface parts में _parse_ करता है, इसे “Parser” connector के रूप में identify करना appropriate लगता है।

एक बार usable parts place हो जाएँ, next connection Layer 5, “Components, Controls, & Layouts,” और Layer 4, “Graphs & Frames” के बीच होती है। Layer 5 describe कर सकती है कि interface में क्या है और वे parts कैसे behave करें, लेकिन Layer 4 को वह information larger context में organized चाहिए। इसका मतलब है कि उनके बीच का connector interface parts को लेकर उन्हें ऐसी relationships में place करे जिन्हें tracked, coordinated, और next stage के लिए prepared किया जा सके। button, उदाहरण के लिए, control के रूप में already exist कर सकता है, लेकिन उसे rest of interface complete scene का part मान सके उससे पहले position, size, state, और surrounding frame से relationship चाहिए। क्योंकि यह connector usable interface parts को graph और frame structures में _adapt_ करता है, हम इसे “Adapter” connector कह सकते हैं।

वहाँ से organized frame को Layer 3, “Renderers,” से communicate करना होता है, Layer 4, “Graphs & Frames” के connection through। Layer 4 describe कर सकती है कि interface में क्या exist करता है और हर part whole से कैसे relate करता है, लेकिन Layer 3 को ऐसी instructions चाहिए जिन्हें वह produce कर सके। इसका मतलब है कि उनके बीच का connector organized scene को specific rendering system के लिए suitable work में translate करे। visual interface में, frame के अंदर button को screen पर appear होने से पहले rectangles, textures, glyphs, या draw commands में convert करना पड़ सकता है। क्योंकि यह connector organized interface और उसे produce करने वाले renderer को _bridge_ करता है, हम इसे “Bridge” connector कह सकते हैं।

renderer ने अपना work prepare कर लिया हो, तो next connection Layer 3, “Renderers,” और Layer 2, “Windows” के बीच दिखाई देती है। Layer 3 जान सकती है कि draw, play, या otherwise produce कैसे करना है, लेकिन उसे अभी भी target चाहिए जहाँ वह work deliver कर सके। Layer 2 वह view provide करती है जिसके through user उसे receive करता है, इसलिए उनके बीच का connector renderer को result भेजने के लिए usable place expose करे। OpenGL, उदाहरण के लिए, scene draw कर सकता है, लेकिन image user को appear हो सके उससे पहले उसे रखने की जगह चाहिए। क्योंकि यह connector वह _surface_ provide करता है जहाँ rendered work window से मिलता है, हम इसे “Surface” connector कह सकते हैं।

आखिर में, Stack के bottom को Layer 2, “Windows,” और Layer 1, “Systems” के बीच communication चाहिए। इस point पर connector को जिस form में Layer 1 naturally समझती है, उसी में काम करना होता है, चाहे वह operating-system handle, platform API, device signal, या physical mechanism हो। desktop application में यह Layer 2 को create और manage करने वाला native handle हो सकता है। automatic door में यह built-in sensor और motor connection हो सकता है जो doorway को respond करने देता है। क्योंकि यह connector system से उसकी अपनी _native_ form में communicate करता है, हम इसे “Native” connector identify करेंगे।

### Model में Connectors की भूमिका

अब हर connector identify होने के बाद, हम Model की movement को अधिक complete ढंग से describe कर सकते हैं। top to bottom, connectors हैं “Data,” “Parser,” “Adapter,” “Bridge,” “Surface,” और “Native.” हर एक Stack की दो explicit layers के बीच बैठता है और explain करता है कि वे layers कैसे communicate करती हैं। Data connector stored content को ऐसी structure में लाता है जिसे Model समझ सके। Parser connector उस structure को usable interface parts में turn करता है। Adapter connector उन parts को graphs और frames में place करता है। Bridge connector उन organized structures को renderer के लिए prepare करता है। Surface connector renderer को result deliver करने की जगह देता है। अंत में, Native connector window को system से system के अपने terms में communicate करने देता है।

### Connectors और Living Exchange

मिलकर ये connectors Stack द्वारा described path को complete करते हैं। layers हमें बताती हैं कि information flow में कहाँ है, जबकि connectors बताते हैं कि वह एक step से next step तक कैसे move करती है। यही CatalystUI Model को static arrangement of parts से अधिक describe करने देता है। यह living exchange describe करता है: stored content structure बनता है, structure interface बनता है, interface output बनता है, output user तक पहुँचता है, और user का response उसी pattern से वापस travel कर सकता है। क्योंकि connectors को layers themselves redefine किए बिना replace या rework किया जा सकता है, वे Model को उसकी सबसे important strengths में से एक देते हैं: different devices, domains, और systems के साथ adapt करने की क्षमता, जबकि वही underlying flow of information preserved रहता है।
